# 033-02 DMARCの設定とAmazon SES本番アクセス申請（実装ログ）

## 1. 目的と対象

前章[033-01](./033-01-amazon-ses-domain-dns-development-log.md)では、Amazon SESに`chinese-output-forge.com`を登録し、Route 53へDKIM・SPF・カスタムMAIL FROM用のDNSレコードを追加した。

今回は、独自ドメインのDMARCポリシーをRoute 53へ登録するとともに、Amazon SESのサンドボックス制限を解除するため本番アクセスを申請した。実装時の記録に基づき、申請内容、AWSからの追加確認、承認、およびDMARCレコードの設定をまとめる。

## 2. Amazon SESの本番アクセスを申請

SESで送信ドメインが「検証済み」になっても、サンドボックス環境では送信先に制限がある。Chinese Output Forgeでは会員登録したユーザーにパスワード再設定などのメールを送信するため、本番アクセスを申請した。

SESコンソールで「設定を始める」から「本番アクセスをリクエスト」を選択した。

![](../../images/0033-69.png)

申請画面では、次の内容を入力した。

![](../../images/0033-70.png)

| 項目 | 申請内容 |
|---|---|
| メールタイプ | トランザクション |
| ウェブサイトURL | `https://chinese-output-forge.com` |
| その他の連絡先 | 任意項目 |
| 連絡時の希望言語 | 日本語 |
| AWSサービス条件・AUP | 内容を確認して同意 |

「リクエストの送信」を実行し、本番アクセスの申請が受け付けられた。申請直後は審査中であり、サンドボックスが解除された状態ではなかった。

## 3. AWSからの追加情報の依頼に対応

申請後、AWSから追加情報を求める通知が届いた。表示されたケースIDを使用してAWSサポートセンターのケースを開き、質問内容を確認した。

![](../../images/0033-71.png)

![](../../images/0033-72.png)

AWSから確認された内容は、次の6点だった。

1. メール送信に関連するWebサイトまたはアプリケーションのURL
2. 送信するメールの種類
3. 1日または1か月あたりの送信量
4. メール受信者の取得方法
5. バウンスおよび苦情の管理方法
6. 送信予定のメールのサンプルまたは内容

これに対して、Chinese Output Forgeの利用形態に基づいて以下の情報を回答した。

| 確認事項 | 回答内容 |
|---|---|
| Webサイト | `https://chinese-output-forge.com` |
| メールの種類 | パスワード再設定など、ユーザー操作を契機とするトランザクションメールのみ。マーケティングメールは送信しない |
| 送信量 | 個人開発アプリのため、当初は1日数通程度を想定 |
| 受信者 | 自らアカウント登録したユーザーが登録したメールアドレスのみ。購入リストなどは使用しない |
| バウンス・苦情 | SESの送信状況・アカウントレベルの抑制リストなどを利用し、不要な再送信を防止する方針 |
| メール内容 | パスワード再設定のリクエストを受け付け、再設定ページへのリンクを案内するメール |

メールのサンプルとして、件名「パスワード再設定のご案内」と、ユーザー自身の操作に応じて再設定リンクを案内する旨を記載した。

さらに、利用リージョンが東京（`ap-northeast-1`）であり、`chinese-output-forge.com`は同リージョンのSESで検証済みであることを伝えた。

AWSサポートケースから回答を送信し、追加情報の提出を完了した。この時点では再審査中だったが、元の記録にはその後「承認された」と記載されている。承認日時や通知の詳細は記録されていない。

## 4. Route 53にDMARCレコードを追加

独自ドメイン`chinese-output-forge.com`について、DMARCのTXTレコードをRoute 53のホストゾーンへ追加した。

設定値は次のとおり。

| 項目 | 設定値 |
|---|---|
| レコード名 | `_dmarc.chinese-output-forge.com` |
| レコードタイプ | `TXT` |
| 値 | `v=DMARC1; p=none;` |
| TTL | 300秒 |

Route 53で上記の内容を入力し、「作成」を実行した。元の記録では、DNSレコードが正常に作成されたことを確認している。

今回は、実際に送信したメールのDMARC認証結果をまだ確認していない段階だったため、DMARCに失敗したメールの隔離・拒否を要求しない`p=none`から開始した。`p=quarantine`や`p=reject`への変更はこの章では実施していない。

## 5. 作業結果と次の工程

この章では、Amazon SESの本番アクセスを申請し、追加情報の依頼に対応した。元ログには最終的に承認されたことが記録されている。また、Route 53にDMARC用TXTレコードを追加した。

一方、メール送信時のSPF・DKIM・DMARCの実際の認証結果や、Spring Bootからのメール送信については、この時点では検証していない。次章以降で、アプリケーション側の送信処理をAmazon SESへ切り替える。

> **学習ログに分ける内容**：Header FromとEnvelope Fromの違い、SPF・DKIM・DMARCの認証とAlignment、DMARCポリシーの考え方。実装ログでは設定内容と申請・確認の経緯を中心に記録した。
