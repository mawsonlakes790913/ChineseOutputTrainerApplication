# 032-05 AWS低コスト構成⑤｜旧環境の削除とAWSリソースの依存関係（学習ログ）

## はじめに

前回の032-04では、新しいSingle Instance環境に合わせたCloudWatch Alarmの見直しを振り返った。

今回は、新環境の動作確認後に実施した旧Load Balanced環境と不要リソースの削除について整理する。特に、**旧環境を削除するタイミング**、**Elastic Beanstalkが管理するリソースの範囲**、**削除後に何を確認する必要があるか**を学習内容として残す。

## 1. 旧環境は切り替えが完了するまで残しておく

新しいSingle Instance環境を作成した段階では、旧Load Balanced環境を削除しなかった。

新環境のRDS接続、Route 53の切り替え、HTTPS対応が正常に動作するか確認する必要があったためである。問題が発生した場合に戻せるよう、旧環境をロールバック先として維持した。

今回の移行では、**新環境を構築すること、アクセス先を切り替えること、旧環境を削除することを別々の段階として扱った**。

リソースを早く削除すればその分コストは下がるが、切り替えが完了する前に削除すると復旧の選択肢が減る。低コスト化の作業でも、削除のタイミングには注意が必要だと分かった。

## 2. Elastic Beanstalk環境と配下のリソースを区別する

旧環境はElastic BeanstalkのLoad Balanced構成であり、EC2だけでなく、Auto Scaling Group、ALB、Target Group、Security Groupなどと関係していた。

ここで重要なのは、**アプリケーションを動かしているEC2だけがElastic Beanstalk環境ではない**という点である。

旧EC2を個別に削除することと、Elastic Beanstalk環境を終了することは同じではない。Elastic Beanstalkが管理しているリソースと、それ以外に残るリソースを区別して作業する必要があった。

今回の実装では、まず旧Elastic Beanstalk環境を終了し、その後でEC2・ALB・Target Groupなどの削除状況を確認した。

この経験から、**リソースを削除するときは、個々のリソースだけでなく、その管理元と依存関係を把握する必要がある**と理解した。

## 3. 「旧環境の終了」と「不要リソースの整理」は別の作業

Elastic Beanstalk環境を終了しただけで、移行前に利用していたAWSリソースがすべて不要な状態になるとは限らない。

今回の低コスト化では、旧環境で使用していたNAT GatewayやElastic IP、Private App Subnet、Route Table、Security Group、監視設定なども整理対象となった。

一方、RDSやPrivate DB Subnetなど、新しい構成でも必要なものは維持する必要がある。

したがって、単純に「旧環境に関係するものを全部削除する」のではなく、**新環境から引き続き参照されているか**を判断基準とした。

特にSecurity Groupは、RDS側に旧EC2のSecurity Groupを参照する許可ルールが残っている場合がある。新旧環境の移行中は両方を許可し、旧環境の廃止後に不要な参照を整理するという順序が重要だった。

## 4. Single InstanceでもAuto Scaling Groupの扱いに注意する

Elastic BeanstalkのSingle Instance構成では、ALBを使用せずEC2を1台で稼働させる。

ただし、**Single Instanceだからといって、Elastic Beanstalkによる環境管理の仕組みがすべてなくなるわけではない**。

今回の削除対象は旧Load Balanced環境であり、新しい`Chinese-output-forge-single-env`は引き続き稼働させる必要があった。

リソース一覧にAuto Scaling Groupなどが見つかった場合も、名前や関連付けを確認せずに削除すると、現在稼働中の環境へ影響する可能性がある。

**削除してよいかどうかはリソースの種類だけで判断せず、どの環境に属しているかを確認する**ことが重要だと学んだ。

## 5. 削除後は「残っていないこと」と「残っていること」を確認する

今回の目的は、旧環境のリソースを削除すること自体ではなく、Chinese Output Forgeを低コスト構成で継続運用できる状態にすることだった。

最終的に残す構成は、次のとおりである。

- Elastic BeanstalkのSingle Instance環境とEC2：1台
- RDS：Single-AZ
- Public App Subnet：1つ
- Private DB Subnet：2つ（DB Subnet Groupのために維持）
- Route 53：新EC2のElastic IPを参照
- CloudWatch・SNS：新環境向けの監視と通知に利用

そのため、削除作業の結果は二つの方向から確認する必要があった。

一つは、旧EC2、ALB、Target Group、NAT Gatewayなど、**不要になったリソースが残っていないこと**。もう一つは、新EC2、RDS、必要なサブネット、DNS、監視設定など、**稼働に必要なリソースが維持されていること**である。

AWSコンソール上でリソースが消えたことだけでは、アプリケーションが引き続き正常に動作することまでは保証されない。インフラ構成の確認とアプリケーションの動作確認は、別の観点として考える必要がある。

## まとめ

旧環境の削除を通じて、AWSの低コスト化は単にリソースの台数を減らす作業ではなく、**管理元・依存関係・移行順序を考慮して、必要な構成だけを残す作業**だと理解した。

今回特に重要だったのは、旧環境をロールバック先として維持したこと、Elastic Beanstalk環境とその配下のリソースを区別したこと、そして削除対象だけでなく維持対象も確認したことである。

次の032-06では、低コスト構成への移行後に実施したRDSのAvailability Zone変更と、最終的な動作確認について振り返る。
