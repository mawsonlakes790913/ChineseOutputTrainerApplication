# 019 AI問題生成モードの実装その5 AI生成処理の改善

前チャプターまでで、生成元問題をAIへ送り、生成された問題を`AiGeneratedQuestionDto`へ変換して問題画面へ表示できるようになった。

このチャプターでは、実際にAI問題生成モードを繰り返し動作させながら、以下の改善を行った。

1. AI生成問題と生成元問題を比較できるようにする
2. AI生成結果の偏りを改善する
3. AI問題生成完了までの待機時間を短縮する

特に2と3については、一度の修正で完成したわけではない。

```text
問題を発見
↓
原因を考える
↓
修正
↓
実際に生成して確認
↓
残った問題を特定
↓
次の修正
```

を何度も繰り返しながら、最終的な生成方式を決めた。

---

# 1. AI生成問題と生成元問題を比較できるようにした

AI生成問題だけを表示している状態では、生成された問題が元の問題からどのように変更されたのか確認しにくかった。

そこで、`AiGeneratedQuestionDto`へ生成元問題を保持するフィールドを追加した。

```java
private String sourceJapaneseText;

private String sourceChineseText;
```

`convertToGeneratedQuestions()`では、`sourceIndex`から取得した生成元の`Question`を利用して設定する。

```java
generatedQuestion.setSourceJapaneseText(
        sourceQuestion.getJapaneseText());

generatedQuestion.setSourceChineseText(
        sourceQuestion.getChineseText());
```

問題画面にも生成元問題を追加し、「解答を見る」を押した後にAI生成問題と一緒に確認できるようにした。

![](../../images/0019-01.png)

さらに、中国語同士を比較しやすいよう、生成元問題については中国語文→日本語文の順で表示するよう修正した。

![](../../images/0019-02.png)

これによって、以降の検証では、

```text
生成された中国語
生成元の中国語
```

を直接比較しながら、AIがtemplateの制約を守っているか、同じ語彙へ偏っていないかなどを確認できるようになった。

---

# 2. AI生成結果の偏りを改善した

## 2-1. 同じ条件で複数回生成して偏りを確認した

まず、同じ生成条件で複数回問題を生成し、どの程度結果が変化するのか確認した。

初級9問について比較すると、1回目と2回目の結果は、

```text
内容が全く一致しない：3問
一部一致する：3問
完全一致する：3問
```

となった。

ただし、すべての一致を同じ問題として扱うことはできない。

例えば、

```text
{subject}騎{noun}去{noun}了。
```

では、`騎`と自然に組み合わせられる乗り物自体が限られる。

同様に、

```text
{subject}搭{noun}去{noun}。
```

についても、`搭`と自然に組み合わせられる交通手段にはある程度の制限がある。

そのため、

```text
自然な候補自体が少ないために重複する問題
```

と、

```text
十分な候補が存在するのにAIが特定の語彙へ偏っている問題
```

を分けて考える必要があると判断した。

---

## 2-2. 共通プロンプトで生成結果の多様性を指定した

まず、共通プロンプトへ生成語彙の多様性に関するルールを追加した。

人物、職業、場所、物品、行動、形容詞などについて、templateの制約を満たす範囲で幅広い候補から選択し、毎回典型的な同じ語彙へ偏らないよう指示した。

ただし、多様性を強く要求しすぎると、

```text
騎 + 不自然な乗り物
搭 + 不自然な交通手段
```

のような問題を生成する可能性がある。

そのため、

```text
自然さ・正確さ ＞ 多様性
```

という優先順位を明確にした。

### 気づいた点・勉強になった点

生成AIでは、制約を強くすれば必ず品質が上がるわけではない。

今回のアプリは語学教材なので、毎回違う問題を生成することよりも、自然で正確な中国語を生成することの方が重要である。

AIへ複数の要求を与える場合は、それぞれの要求だけでなく、

```text
何を最優先するのか
```

もプロンプト上で明確にする必要があると分かった。

---

## 2-3. 元問題の語句を再利用できる`_reusable`を考えた

当時の共通プロンプトでは、プレースホルダに対応する元問題の語句を原則として再利用しないよう指定していた。

しかし、

```text
他騎腳踏車去學校了。
```

に対する、

```text
{subject}騎{noun}去{noun}了。
```

のような問題では、すべてのプレースホルダを毎回変更する必要はない。

そこで、

```text
{subject}
→ 元問題の主語を再利用しない

{subject_reusable}
→ 元問題の主語を再利用してもよい
```

という区別を追加した。

同じ考え方で、

```text
{subject_reusable}
{noun_reusable}
{noun_phrase_reusable}
{verb_reusable}
{verb_phrase_reusable}
{adjective_reusable}
{predicate_reusable}
```

を用意した。

`_reusable`は、

```text
元の語句を必ず使用する
```

という意味ではなく、

```text
元の語句を使用してもよい
```

という意味とした。

### 工夫した点

「再利用してよいか」と「どの程度再利用するか」は別の責務として扱った。

```text
template
→ そのプレースホルダで再利用してよいか

共通プロンプト
→ _reusableをどの程度再利用するか
```

とした。

例えば、

```text
{subject_reusable_33}
```

のように確率までtemplateへ記述すると、再利用率を変更したくなった場合に多数のQuestionを修正する必要がある。

そのため、templateには「再利用可能」という性質だけを持たせ、再利用の程度は共通プロンプトから一括して調整できるようにした。

---

## 2-4. `_reusable`導入後の生成結果を確認した

一部のQuestionのtemplateを`_reusable`へ変更し、再度同じ条件で問題を生成した。

元問題の語句を維持しても問題ない箇所については、

```text
他騎腳踏車去圖書館了。
```

のように、元の語句を残しながら別の部分を変更できるようになった。

一方で、

```text
這部電影很感人。
她是一名護理師。
週末我要跟朋友去吃火鍋。
```

など、以前と同じ、または非常に似た結果も依然として生成された。

つまり、`_reusable`によって不要な語彙変更を抑えることはできたが、

```text
AIが特定の語彙を選びやすい
```

という問題そのものはほとんど改善しなかった。

そこで、AIに最終回答を1つだけ生成させる方式を見直すことにした。

---

## 2-5. 1つの生成元問題から3候補を生成する方式を考えた

1候補だけを要求すると、AIが最も生成しやすい典型的な回答へ収束している可能性があると考えた。

そこで、

```text
AI
↓
1つの生成元問題から3候補生成
↓
Java
↓
3候補からランダムに1つ選択
```

する方式を実装した。

`TemporaryGeneratedQuestionDto`へ、

```java
private int candidateIndex;
```

を追加する。

AIからは、

```text
sourceIndex=0, candidateIndex=0
sourceIndex=0, candidateIndex=1
sourceIndex=0, candidateIndex=2

sourceIndex=1, candidateIndex=0
sourceIndex=1, candidateIndex=1
sourceIndex=1, candidateIndex=2
```

のように取得する。

Java側では、

```java
Random random = new Random();
```

を作成し、

```java
int randomIndex = random.nextInt(3);
```

によって`0～2`の候補番号を決める。

その後、

```java
if (temporaryGeneratedQuestionDto.getSourceIndex() == sourceIndex
        && temporaryGeneratedQuestionDto.getCandidateIndex() == randomIndex) {
```

として、生成元問題と候補番号の両方が一致する問題を取得する。

GeminiのSchemaにも`candidateIndex`を追加した。

### 工夫した点

AI自身に3候補から1つを選ばせるのではなく、AIには3候補すべてを返させ、最終的な選択をJava側で行うようにした。

これによって、

```text
AIがどの候補を最終回答として選びやすいか
```

という傾向から候補選択処理を切り離した。

また、1生成元問題につき3件の`TemporaryGeneratedQuestionDto`が存在するようになったため、単純にListを先頭から処理するのではなく、

```text
sourceIndex
+
candidateIndex
```

の組み合わせから対象を特定する必要があることも理解できた。

---

## 2-6. 3候補方式を初級問題で検証した

3候補方式を実装した後、同じ初級問題を複数回生成した。

一見すると、

```text
週末我要跟同學去逛夜市。
週末我要跟朋友去看表演。
週末我要跟家人去看展覽。
週末我要跟朋友去吃火鍋。
```

のように、以前より異なる結果が得られる問題もあった。

一方で、

```text
這部電影很{adjective}。
```

では`感人`など、

```text
{subject}是一名{noun}。
```

では`設計師`などが繰り返し現れた。

3候補方式で改善する問題と、ほとんど改善しない問題が存在することが分かった。

---

## 2-7. 特に偏りの大きい問題だけを繰り返し生成した

偏りが疑われた問題について、さらに生成回数を増やして確認した。

その結果、

```text
請問，{noun}在哪裡？
```

では`服務台`、

```text
這部電影很{adjective}。
```

では`精彩`、

```text
這個{noun}多少錢？
```

では`蘋果`や`便當`

が非常に高い頻度で生成された。

3候補の中から選択しているのはJavaの`Random`なので、最終結果がここまで偏るということは、

```text
Javaが同じ候補を選択している
```

のではなく、

```text
AIが生成している3候補自体が
毎回似た顔ぶれになっている
```

可能性が高いと考えた。

### 気づいた点・勉強になった点

ランダム性を追加する場所を間違えると、期待した効果が得られないことが分かった。

今回Java側でランダムに選択できるのは、

```text
AIがすでに作った3候補
```

の中だけである。

AIが毎回ほぼ同じ3候補を作っているなら、その後でどれだけランダムに選択しても、最終的な出力範囲は広がらない。

つまり、

```text
候補を選択する処理
```

と、

```text
候補集合そのものを多様化する処理
```

は別問題である。

---

## 2-8. 上級問題でも3候補方式を検証した

初級だけの問題なのか確認するため、上級問題についても複数回生成した。

上級問題は文が長く、変更可能な要素も多いため、

```text
這項政策會對{noun}造成什麼樣的影響，目前還很難判斷。
```

や、

```text
要解決這個問題，除了{noun}之外，也必須考量{noun}。
```

など、多くの問題では比較的多様な結果を生成できた。

一方で、

```text
隨著{noun}越來越{adjective}，
{noun}也需要採取更有{adjective}的因應方式。
```

では、最後の`{adjective}`に元問題の`彈性`が繰り返し使用された。

この箇所には`_reusable`を付けていないため、本来は別の語彙へ変更させたい箇所である。

ここで、AIの生成傾向だけではなくtemplate自体を確認する必要があると考えた。

---

## 2-9. template自体が生成候補を制限していることに気づいた

問題となったtemplateは、

```text
隨著{noun}越來越{adjective}，
{noun}也需要採取更有{adjective}的因應方式。
```

だった。

最後の部分が、

```text
更有{adjective}的因應方式
```

となっているため、自然に使用できる形容詞がかなり限定される。

つまり、AIへ、

```text
別の形容詞を使用すること
```

と要求しながら、template側では自然な候補がほとんど存在しない構造を与えていた。

そこで、

```text
隨著{noun}越來越{adjective}，
{noun}也需要採取更{adjective}的因應方式。
```

へ変更し、最後の形容詞に入れられる語彙の範囲を広げた。

### 気づいた点・勉強になった点

AIの出力がおかしいとき、プロンプトだけを疑ってはいけないことが分かった。

AIへ渡しているtemplate自体が候補を狭めているなら、プロンプトで多様性を要求しても根本的には解決できない。

今回のような生成AI機能では、

```text
プロンプト
AIモデル
Java側の処理
入力データ
template
```

をそれぞれ分けて原因を考える必要がある。

---

## 2-10. `{classifier}`を追加してtemplateの自由度を広げた

同様の問題は、

```text
這個{noun}多少錢？
```

にも存在した。

`個`を固定したまま`{noun}`だけを変更すると、`個`と自然に組み合わせられる名詞へ候補が限定される。

そこで、新しく、

```text
{classifier}
```

を追加し、

```text
這{classifier}{noun}多少錢？
```

とした。

これによって、

```text
這罐牛奶多少錢？
這包餅乾多少錢？
這盒草莓多少錢？
```

のように、量詞と名詞の組み合わせそのものを変更できる。

### 工夫した点

`{classifier}`と`{noun}`を完全に独立して生成させると、

```text
量詞単体では正しい
名詞単体でも正しい
しかし組み合わせると不自然
```

という問題が発生する可能性がある。

そこで、共通プロンプトには、

```text
{classifier} + {noun}
```

を自然な組み合わせとして生成するよう指定した。

単純に変更可能な箇所を増やすだけでなく、複数のプレースホルダ間に意味的な関係がある場合は、その関係もAIへ伝える必要がある。

# 3. AI問題生成完了までの待機時間を短縮した

## 3-1. 処理時間を分解して計測した

3候補方式では、生成結果の改善と引き換えに問題生成完了までの待ち時間がかなり長くなった。

そこで、まず、

```text
入力作成
AI API
DTO変換
合計
```

の処理時間をそれぞれ計測した。

`System.currentTimeMillis()`を使い、各処理の開始・終了時刻から時間を取得した。

結果として、入力作成やDTO変換は非常に短く、処理時間の大部分をAI APIが占めていることが分かった。

### 気づいた点・勉強になった点

処理が遅いときに、感覚だけで最適化対象を決めるべきではない。

今回Java側のfor文などを改善しても、全体の処理時間にはほとんど影響しない。

まず実測して、

```text
どこがボトルネックなのか
```

を特定してから改善する必要があると分かった。

---

## 3-2. ChatGPTを3候補から1候補へ戻して速度を比較した

3候補生成がどの程度処理時間へ影響しているか確認するため、一度1候補方式へ戻した。

結果は以下となった。

| 条件 | 3候補 | 1候補 |
|---|---:|---:|
| 初級9問 | 49.444秒 | 18.253秒 |
| 上級6問 | 66.116秒 | 29.450秒 |
| 全23問 | 174.318秒 | 66.670秒 |

3候補から1候補へ戻すことで、API時間を約55～63%削減できた。

Java側の処理ではなく、AIへ生成させる文章数が待機時間へ大きく影響していることが確認できた。

---

## 3-3. template改善後なら1候補でも十分か再検証した

3候補方式を導入した後にtemplate自体も改善していた。

そのため、

```text
以前1候補方式で偏った
```

からといって、

```text
現在のtemplateでも1候補方式では偏る
```

とは限らない。

そこで、改善済みtemplateを使用した状態でもう一度1候補方式を試した。

しかし、実際に生成すると特定の語彙へ偏る問題が再び確認された。

つまり、template改善だけでは1候補方式の偏りを十分に解消できなかった。

---

## 3-4. Geminiの1候補方式を検証した

次に、AIモデルをChatGPTからGeminiへ変更して1候補方式を試した。

GeminiではChatGPTより短時間で生成でき、速度面では大きな改善が見られた。

一方で、生成結果については特定の語彙へ偏る問題が残った。

つまり、

```text
ChatGPT → Gemini
```

というモデル変更だけでは、生成結果の多様性は解決しなかった。

---

## 3-5. Geminiでも3候補方式を検証した

Geminiを使用したまま3候補方式へ戻して検証した。

ChatGPTの3候補方式ほど極端に処理時間は長くならなかったため、速度面では一定の改善があった。

しかし、生成結果の多様性については期待したほど改善せず、ChatGPTの3候補方式より偏りが目立つケースもあった。

ここまでの検証から、

```text
候補数を増やすことで
多様性を確保する
```

という方式自体に限界があると判断した。

---

## 3-6. 過去の生成結果を利用する方式へ発想を変更した

ここで、以前は実装規模が大きいとして見送っていた、

```text
過去の生成結果を保存
↓
次回生成時にAIへ渡す
↓
過去の問題と異なる問題を生成
```

という方式を改めて採用することにした。

3候補方式では、毎回3倍の文章を生成する必要がある。

一方で生成履歴を利用すれば、

```text
1候補だけ生成
+
過去の結果を避ける
```

ことで、多様性と速度を両立できる可能性がある。

---

## 3-7. `ai_generation_history`を実装した

生成結果を保存するため、

```text
ai_generation_history
```

を追加した。

履歴は、

```text
ユーザー
生成元Question
生成された中国語文
生成日時
```

を保持する。

また、AIへ送る`AiGenerationSourceDto`へ、

```java
private List<String> generationHistory;
```

を追加した。

Repositoryでは、ユーザーと生成元問題から直近の履歴を取得する。

最初は3件とした。

```java
List<AiGenerationHistory>
findTop3ByUserIdAndQuestionQuestionIdOrderByCreatedAtDesc(
        Long userId,
        Long questionId);
```

### 工夫した点

`AiGenerationSourceDto`には、

```java
List<AiGenerationHistory>
```

をそのまま持たせず、

```java
List<String>
```

として生成された中国語文だけを持たせた。

`AiGenerationHistory`はDBへ永続化するためのEntityであり、AIが必要なのは過去に生成された中国語文だけだからである。

```text
Repository
↓
AiGenerationHistoryを取得
↓
chineseTextだけ取り出す
↓
AiGenerationSourceDto
↓
AI
```

とすることで、永続化用のEntityとAI入力用DTOの役割を分けた。

### 気づいた点・勉強になった点

DTOには取得したデータをそのまま詰め込むのではなく、

```text
そのDTOを使う処理に必要な情報
```

だけを持たせるべきだと分かった。

また、Spring Data JPAでは、

```java
findTop3ByUserIdAndQuestionQuestionIdOrderByCreatedAtDesc(...)
```

のように、`Top3`、関連Entityのフィールド、`OrderBy...Desc`までメソッド名で表現できることも確認した。

---

## 3-8. 直近3件の`generationHistory`で検証した

3候補方式を廃止し、

```text
Gemini
+
1候補
+
直近3件のgenerationHistory
```

で生成した。

1候補方式なので3候補方式より高速でありながら、履歴なしの1候補方式より生成結果の多様性は改善した。

しかし、履歴から外れた結果が再び生成されるケースがあった。

直近3件しか見ていないため、

```text
1
2
3
4
1に似た結果
```

のように、以前の生成内容へ戻る可能性がある。

そこで履歴数を増やすことにした。

---

## 3-9. `generationHistory`を5件へ増やした

Repositoryを、

```java
findTop5ByUserIdAndQuestionQuestionIdOrderByCreatedAtDesc(...)
```

へ変更し、共通プロンプトも最大5件の履歴を受け取るよう修正した。

再度複数回生成すると、3件の場合よりさらに多様性が改善した。

一方で、一部の問題では5件の履歴から外れた後に以前と似た結果へ戻るケースが残った。

そのため、さらに履歴数を増やして速度への影響を確認することにした。

---

## 3-10. 主語の偏りをtemplate側から制御するよう変更した

`generationHistory`によって同じ文章の繰り返しは改善したが、生成内容を確認すると、

```text
爸爸
媽媽
哥哥
妹妹
```

など、家族を表す主語へ偏る問題があった。

プロンプトで「主語を多様にする」と要求するだけでは十分に改善しなかったため、主語の種類をtemplateから制御する方式へ変更した。

最終的に、

| プレースホルダ | 代名詞 | 非代名詞 | 家族語 | 人名 |
|---|:---:|:---:|:---:|:---:|
| `{subject}` | ○ | ○ | × | × |
| `{subject_pronoun}` | ○ | × | × | × |
| `{subject_non_pronoun}` | × | ○ | × | × |
| `{subject_family}` | ○ | ○ | ○ | × |

とした。

### 工夫した点

これまでは主語について、

```text
template
+
SubjectType
```

の両方から制御していた。

しかし、

```text
{subject_pronoun}
{subject_non_pronoun}
{subject_family}
```

のようにプレースホルダ自体へ意味を持たせれば、templateだけで使用可能な主語の種類を表現できる。

生成ルールを複数の情報へ分散させず、可能な範囲でtemplateへ集約した。

---

## 3-11. `SubjectType`・`verbVariation`・`_reusable`を廃止した

主語制御をtemplateへ統合したことで`SubjectType`は不要になった。

また、動詞に関する変更範囲もtemplateの固定部分とプレースホルダによって制御できるため、`verbVariation`も不要と判断した。

さらに、`generationHistory`によって生成結果の多様性を確保できるようになったため、途中で導入した`_reusable`も役割が薄れた。

そこで、

```sql
ALTER TABLE question
DROP COLUMN subject_type,
DROP COLUMN verb_variation;
```

としてDBから不要なカラムを削除し、プロンプトもtemplate中心の構成へ整理した。

### 気づいた点・勉強になった点

実装中に新しい問題が見つかるたびに仕組みを追加していくと、

```text
SubjectType
verbVariation
_reusable
generationHistory
template
共通プロンプト
```

のように制御方法が増えていく。

しかし、新しい仕組みを追加した結果、以前の仕組みが不要になることもある。

今回も、

```text
主語用placeholderを詳細化
→ SubjectTypeが不要

templateによる制御を整理
→ verbVariationが不要

generationHistoryを導入
→ _reusableが不要
```

となった。

機能追加だけでなく、役割が重複した古い仕組みを削除することも設計を単純に保つために必要だと分かった。

---

## 3-12. `generationHistory`を10件へ増やした

履歴をさらに、

```java
List<AiGenerationHistory>
findTop10ByUserIdAndQuestionQuestionIdOrderByCreatedAtDesc(
        Long userId,
        Long questionId);
```

として10件へ増やした。

共通プロンプトについても、`generationHistory`は新しい順に最大10件含まれるよう修正した。

複数回生成した結果、5件の場合よりさらに多様性が改善した。

また、履歴を10件へ増やしても生成時間への大きな悪影響は確認できなかった。

そのため、

```text
直近10件
```

を採用した。

### 気づいた点・勉強になった点

履歴件数については、最初から10件と決めたのではなく、

```text
3件
↓
実行・確認
↓
5件
↓
実行・確認
↓
10件
↓
実行・確認
```

と段階的に決めた。

生成AIの結果は確率的なので、1回の出力だけで仕様を決めるのではなく、複数回生成して傾向を確認する必要がある。

また、重複を完全に0にすることは目標にしなかった。

過去のすべての問題をAIへ渡したり、過去に登場した単語をすべて禁止したりすれば、プロンプトが複雑になり、自然な文章を生成するための選択肢まで狭くなる。

このアプリでは、

```text
絶対に重複しない
```

より、

```text
学習時に十分なバリエーションを得られる
```

ことを優先した。

## 3-13. GeminiのThinking設定を調べた

ここまでで、

さらにAPI処理時間を短縮できないか調べたところ、GeminiにはThinkingに関する設定があることが分かった。

### 勉強になった点

外部ライブラリの使い方が分からない場合、サンプルコードだけでなくJavadocから型を辿る方法を確認できた。

今回の場合は、

↓

build()

と確認することで、どのようにインスタンスを作成するのか理解できた。

## 3-14. Thinking Levelを`LOW`へ変更した

となった。

## 3-16. `LOW`でも生成品質を維持できるか確認した

Thinking Levelを下げる以上、速度だけでなく生成品質も確認する必要がある。

そこで初級・上級を含め、同じ問題を複数回生成した。

例えば、

```text
我們搭高鐵去高雄吧。
我們搭捷運去夜市吧。
我們搭客運去機場吧。
我們搭渡輪去旗津吧。
```

のように、Language Profileに沿った自然な國語が生成された。

上級問題についても生成結果は十分に多様化しており、「不自然なので問題として採用すべきではない」と判断する文章はほぼ確認されなかった。

そのため、

```text
Thinking Level = LOW
```

を採用することにした。

### 気づいた点・勉強になった点

AIの推論量は高ければ常に良いわけではなく、処理内容に合わせる必要がある。

今回AIへ要求しているのは、

```text
templateを守る
語彙を置き換える
自然な中国語を生成する
日本語訳を生成する
拼音・注音を生成する
```

という比較的明確な処理である。

複雑な推論を必要としない処理で高いThinking Levelを使用すると、品質への効果に対して待機時間だけが増える可能性がある。

ただし、設定を下げて速くなっただけで採用するのではなく、

```text
速度を測定
+
実際の出力品質を複数回確認
```

してから決定する必要がある。

# 4. 今回の実装を通して学んだこと

今回の改善では、最初に考えた方法がそのまま最終実装になったわけではない。

生成結果の偏りについては、

```text
同条件で複数回生成
↓
偏りを確認
↓
共通プロンプトを修正
↓
_reusableを導入
↓
再検証
↓
十分に改善しない
↓
3候補方式を導入
↓
初級問題で検証
↓
偏る問題をさらに10回生成
↓
候補集合自体が偏っていると判断
↓
上級問題でも検証
↓
template自体の問題を発見
↓
template・classifierを修正
```

と進んだ。

待機時間についても、

```text
処理時間を計測
↓
AI APIがボトルネックと判明
↓
ChatGPT 1候補を検証
↓
高速だが偏りが戻る
↓
Gemini 1候補を検証
↓
さらに高速だが偏りが残る
↓
Gemini 3候補を検証
↓
候補数による解決には限界
↓
generationHistoryを導入
↓
履歴3件で検証
↓
履歴5件で検証
↓
生成制御をtemplate中心へ整理
↓
履歴10件で検証
↓
Thinking Levelを調査
↓
LOWへ変更
↓
速度と品質を再検証
```

と段階的に改善した。

その結果、最終的には、

```text
template
↓
変更可能な箇所と語句の種類を制御

generationHistory
↓
過去の生成結果との重複を抑制

Language Profile
↓
普通話・國語として自然な表現を制御

Gemini
↓
1生成元問題につき1問を生成

Thinking Level LOW
↓
必要以上の推論を抑えて高速化
```

という構成になった。

今回特に重要だったのは、一度実装した仕組みに固執しないことである。

`_reusable`や3候補方式は、その時点で確認できていた問題を解決するために意味のある実装だった。

しかし、検証を続けた結果、より適した`generationHistory`方式を実装できたため、最終的には不要になった。

同様に、`SubjectType`や`verbVariation`も、新しいtemplateの設計によって役割を吸収できたため削除した。

```text
実装した
=
今後も残すべき
```

ではなく、

```text
実装
↓
検証
↓
問題発見
↓
改善
↓
必要なら設計変更
↓
不要になった仕組みは削除
```

まで含めて機能を改善していく必要があると学んだ。

また、生成AIを利用する機能では、通常のプログラムと異なり、同じ入力でも毎回同じ結果になるとは限らない。

そのため、

```text
1回正常に生成できた
```

だけでは十分な検証にならない。

同じ条件で繰り返し生成し、

```text
特定の語彙へ偏っていないか
以前と同じ文章へ戻っていないか
templateの制約を守っているか
中国語として自然か
Language Profileを守っているか
処理時間が実用的か
```

を確認する必要がある。

そして、AIの出力を改善するときも、

```text
すべてプロンプトで解決する
```

のではなく、

```text
Java
DB
template
generationHistory
プロンプト
AIモデルの設定
```

のどこで制御するのが適切なのかを考えることが重要だった。

今回の実装では、これらの役割を整理することで、生成結果の自然さ、多様性、生成速度を両立できる構成へ改善することができた。
