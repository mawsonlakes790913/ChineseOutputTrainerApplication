# 032-02 AWS低コスト構成②｜Elastic BeanstalkのSingle Instance移行と502エラーの調査（学習ログ）

## はじめに

Chinese Output Forgeの低コスト構成への移行では、旧Load Balanced環境を残したまま、新しいElastic BeanstalkのSingle Instance環境を構築した。本章では、環境を分けて移行した理由、Elastic Beanstalkが管理するAWSリソースの役割、そして新環境で発生した`502 Bad Gateway`の調査を通じて理解したことを振り返る。

実際の設定操作や画面、動作確認の記録は、対応する[032-02の実装ログ](./032-02-aws-low-cost-elastic-beanstalk-single-instance-implementation-log.md)にまとめている。

## 1. 旧環境を変更せず、新しい環境を作成する理由

旧Load Balanced環境を直接Single Instanceへ変更すると、作業中にアプリケーションが利用できなくなる可能性があった。そのため、新しいPublic Subnet `10.1.12.0/24`にSingle Instance環境を構築し、旧環境を稼働させたまま動作確認を進めた。

この方法であれば、切り替え前に新環境の起動やデータベース接続を確認できる。また、新環境に問題が発生しても、直ちに旧環境を失うわけではない。

**最終的な構成を一度に完成させることよりも、移行中に正常な環境を残しておくことが重要**だと分かった。

## 2. Elastic Beanstalkに任せる部分と自分で設定する部分

Elastic Beanstalkを引き続き利用したため、EC2の作成、アプリケーションのデプロイ、環境管理をすべて手動で行う必要はなかった。

一方で、Elastic BeanstalkがAWSリソースを管理していても、アプリケーションに必要なネットワークやアクセス権限まで自動的に正しく設定されるわけではない。

### サービスロールとEC2インスタンスプロファイルの違い

今回の移行では既存のIAMロールを再利用したが、それぞれの役割を区別する必要があった。

- **Elastic Beanstalkのサービスロール**：Elastic Beanstalk自身がAWSリソースを管理するために使用する。
- **EC2インスタンスプロファイル**：Elastic Beanstalkが作成したEC2に付与するIAMロールに対応し、SSMやParameter Storeなどへのアクセス権限に関係する。

両方ともElastic Beanstalk環境の設定に登場するが、**AWSリソースを管理する主体が異なる**ことを整理できた。

### SSHの接続元を制限する

管理用のSSHをインターネット全体に公開する必要はないため、接続元を`0.0.0.0/0`ではなく、自分のグローバルIPの`/32`に制限した。SSMによる接続手段もあることから、管理目的であっても公開範囲を必要以上に広げない方針とした。

## 3. Elastic IPは手動作成が必要とは限らない

当初は新しいEC2にElastic IPを手動で確保するつもりだった。しかし、実際にはSingle Instance環境の作成に伴い、Elastic IPが割り当てられていた。

これは、事前に考えていた作業と、マネージドサービスが実際に行う作業が必ずしも一致しない例だった。

**自分で作成する予定だったリソースでも、サービス側で既に作成されていないかを確認してから操作する**必要があると学んだ。

## 4. `502 Bad Gateway`をHTTPエラーだけで判断しない

新しい環境のURLへアクセスした際、`502 Bad Gateway`が表示された。画面に表示されたエラーだけを見るとnginxの設定に問題があるようにも見えたが、原因を特定するには、その背後で動作するSpring Bootのログを確認する必要があった。

Elastic Beanstalkの`web.stdout.log`では、Java 21と`prod`プロファイルでSpring Bootが起動を進め、Tomcatが5000番ポートで初期化されていることを確認できた。

一方、データベース接続の処理では、次のエラーが発生していた。

```text
The connection attempt failed.
SocketTimeoutException: Connect timed out
```

つまり、ブラウザから見えていた`502 Bad Gateway`だけでは、障害がnginx自体にあるとは断定できなかった。

**エラーが表示された場所と、実際に処理が失敗した場所は異なることがある。** 今回はアプリケーションログを確認したことで、RDSへの接続に調査対象を絞り込めた。

## 5. Security Groupの許可は新EC2へ自動的に引き継がれない

RDS側のSecurity Groupでは、旧EC2のSecurity GroupからのPostgreSQL通信を許可していた。しかし、新環境のEC2には別のSecurity Groupが付与されていたため、従来の許可ルールだけではRDSへ接続できなかった。

RDS用Security Groupに、新EC2のSecurity Groupを送信元とするTCP `5432`のインバウンドルールを追加すると、アプリケーションへ正常にアクセスできるようになった。

ここで理解したのは、**同じアプリケーションを新しいEC2へデプロイしても、ネットワーク上のアクセス許可は別途確認する必要がある**という点である。

また、旧環境も移行期間中は稼働していたため、旧EC2からの許可ルールはすぐに削除しなかった。まず新EC2からの通信を追加で許可し、動作を確認してから旧環境を整理する順序とした。

この対応によって、**新環境へのアクセス許可を追加することと、旧環境のアクセス許可を削除することは別の段階の作業**だと整理できた。

## 6. 画面表示だけでは移行の成功を判断できない

RDSとの接続問題を解消した後、アプリケーションへアクセスできることに加え、問題の追加と削除を実行した。

画面が表示されるだけなら、データベースを利用する機能が正常に動作しているとは限らない。今回のようにインフラを変更した場合は、実際の読み込み・書き込み・削除を通じて接続先DBとの連携を確認する必要がある。

## 振り返り

今回の移行では、Elastic BeanstalkがEC2などを管理してくれる一方で、IAMロールやSecurity Groupなどの役割を理解して設定を確認する必要があると学んだ。

特に印象に残ったのは、`502 Bad Gateway`の原因が、見た目から想像したnginxの問題ではなく、**新EC2からRDSへの通信を許可していなかったこと**だった点である。エラー画面から推測するだけでなく、Spring Bootのログを確認し、通信経路に沿って原因を絞り込むことの重要性を実感した。

また、旧環境を維持したまま新環境を検証したことで、切り替えと削除を別々に進める移行手順の意味も理解できた。
