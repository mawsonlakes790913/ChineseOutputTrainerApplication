# 032-03 AWS低コスト構成③｜Route 53の切り替えとHTTPS構築で学んだこと（学習ログ）

## はじめに

Chinese Output ForgeをLoad Balanced環境からSingle Instance環境へ移行するにあたり、独自ドメインの接続先を変更し、EC2上でHTTPS通信を受け付けるようにした。本章では、DNSの役割、TLS終端の変更、証明書の選定、nginxの設定調査を通じて理解したことを振り返る。

具体的な設定操作やコマンド、動作確認は、対応する[032-03の実装ログ](./032-03-aws-low-cost-route53-https-implementation-log.md)に記録している。

## 1. DNSの切り替えとHTTPSの設定は別の作業

旧環境では、Route 53のAレコードがALBへのAliasとして設定されていた。新しいSingle Instance環境ではALBを利用しないため、Aliasを無効にしてEC2のElastic IPをAレコードの値に指定した。

ここで理解したのは、**Route 53が担当するのは接続先の名前解決であり、HTTPS通信そのものを中継するわけではない**という点である。DNSでElastic IPを取得した後、クライアントはその接続先へ通信する。

したがって、Aレコードを切り替えただけではHTTPS対応は完了しない。今回はまず`http://chinese-output-forge.com`で新環境への到達を確認し、その後にEC2側のHTTPS設定を進めた。

接続先の切り替えと通信の暗号化を分けて確認したことで、問題が発生した場合にも原因を切り分けやすくなった。

## 2. 変更するDNSレコードを必要最小限にする

Route 53にはWebサイトの接続先を示すAレコード以外にも、NS、SOA、証明書検証用のCNAMEなどが存在する。

今回変更する必要があったのは、Webアクセスの接続先となるAレコードだった。NS、SOA、ACM証明書検証用CNAMEは変更しなかった。

**同じドメインに関係する設定でも、それぞれのDNSレコードの役割は異なる**。構成変更の対象を明確にし、関係のないレコードまで変更しないことが重要だと分かった。

## 3. DNSを切り替えても旧環境をすぐに削除しない

Aレコードを新しいElastic IPへ変更した後も、旧ALBとLoad Balanced環境は残した。

新環境で問題が発生した場合、旧環境へ戻せる状態を維持するためである。移行を進める際には、新環境が動作することと、旧環境を削除してよいことを別々に判断する必要がある。

**DNSの切り替えと旧環境の削除を同時に実施しない**という考え方は、今回の作業で意識した重要な点だった。

## 4. TLS終端を担当するリソースが変わった

高可用性構成では、ALBがクライアントからのHTTPS通信を受け付け、TLSを終端していた。一方、低コスト構成ではALBを廃止したため、EC2上のnginxがその役割を担うことになった。

今回の通信経路は次のようになる。

```text
クライアント
    ↓ HTTPS（443番ポート）
EC2上のnginx（TLS終端）
    ↓ HTTP（localhost:5000）
Spring Boot
```

この構成を考える中で、**HTTPSの証明書を用意することと、nginxからSpring Bootへリクエストを転送することは別の設定**だと整理できた。

証明書を取得しただけでは、443番ポートでの受信やアプリケーションへの転送は始まらない。Webサーバー側にも必要な設定を行う必要がある。

## 5. 証明書の費用と運用負担を分けて考える

EC2側でHTTPS通信を実現する方法として、ACMのエクスポート可能なパブリック証明書を使う案も検討した。しかし、今回の目的はランニングコストの削減であるため、無料で証明書を発行できるLet's Encryptを採用した。

一方、Let's Encryptを利用する場合は、証明書の取得だけでなく、EC2上のnginxへの設定や更新の管理も考える必要がある。

**証明書の発行費用が無料であることと、運用の手間がかからないことは同じではない**。コストを比較するときには、金銭的な負担と管理作業の両方を見る必要があると分かった。

なお、元の学習ログでは証明書の自動更新は今後必要な作業として扱っており、この時点で更新処理の動作確認が完了したとは記録されていない。

## 6. Certbotの動作とnginxの役割を区別する

今回はPythonの仮想環境にCertbotを導入し、Let's Encryptの証明書を取得した。

スタンドアロンモードでは、Certbotが一時的に80番ポートを使用するため、証明書取得前にnginxを停止した。この操作を通じて、証明書の取得時にもHTTP通信を受け付けるポートの使用状況が関係することを理解した。

取得したファイルのうち、`fullchain.pem`は証明書チェーン、`privkey.pem`は秘密鍵としてnginxに設定した。

ただし、これらのファイルが存在するだけでHTTPS通信が成立するわけではない。nginxで証明書を読み込み、TLSを終端する設定を行って初めて、ブラウザからのHTTPSアクセスを受け付けられる。

## 7. nginxの設定ファイルは参考記事のパスを鵜呑みにしない

参考にした記事では`/etc/nginx/conf.d/default.conf`を編集していたが、今回のElastic Beanstalk環境は同じファイル構成ではなかった。

そこで`sudo nginx -T`を実行し、nginxが実際に読み込んでいる設定を確認した。その結果、`/etc/nginx/nginx.conf`が`conf.d/*.conf`を読み込む構成であることが分かり、`/etc/nginx/conf.d/https.conf`を新規作成した。

この経験から、**技術記事の手順をそのまま当てはめるのではなく、現在の環境で有効な設定を確認してから変更すること**が重要だと学んだ。

## 8. リバースプロキシでは元の通信情報も考慮する

nginxでは`listen 443 ssl`でHTTPSを受け付け、`ssl_certificate`と`ssl_certificate_key`で証明書と秘密鍵を指定した。また、`proxy_pass http://localhost:5000`によってSpring Bootへリクエストを転送した。

さらに`X-Forwarded-Proto https`を設定し、nginxの手前ではHTTPSで通信していたことをアプリケーション側に伝えるようにした。

nginxとSpring Bootの間がHTTPであっても、クライアントからnginxまでの通信はHTTPSである。**リバースプロキシを挟む構成では、各区間の通信方式と、アプリケーションへ渡す情報を区別する必要がある**と理解した。

設定反映後はnginxの稼働状態と`https://chinese-output-forge.com`へのブラウザアクセスを確認した。

## まとめ

今回の移行では、単にALBをEC2へ置き換えたのではなく、DNSの参照先とTLS終端の担当を変更した。

特に重要だったのは、**DNSの名前解決、証明書の取得、nginxのHTTPS受付、Spring Bootへの転送を、それぞれ異なる役割として理解すること**である。

また、新旧環境を並行稼働させて切り替え後の確認を行うこと、参考記事の設定ファイルを鵜呑みにせず実環境を調査すること、無料の証明書にも更新・運用の課題があることを学んだ。
