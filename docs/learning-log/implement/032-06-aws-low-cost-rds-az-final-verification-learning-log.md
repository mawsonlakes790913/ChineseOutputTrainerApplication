# 032-06 AWS低コスト構成⑥｜RDSのAvailability Zone変更と移行の振り返り（学習ログ）

## はじめに

前回の032-05では、旧Load Balanced環境と不要になったAWSリソースの削除を振り返った。

今回は、低コスト構成への移行後に行った**RDSのAvailability Zone（AZ）変更**と、アプリケーションの最終確認について整理する。特に、Single-AZ化と配置先AZの指定は別の問題であること、Multi-AZのフェイルオーバーをどのように利用したか、そしてインフラ移行の完了を何によって判断したかを記録する。

## 1. Single-AZ化しても想定したAZに配置されるとは限らない

RDSをMulti-AZからSingle-AZへ変更した後、EC2とRDSの配置先を確認すると、EC2は`ap-northeast-1a`、RDSは`ap-northeast-1c`に存在していた。

同一VPC内で通信できるため、この状態でもアプリケーションは正常に動作していた。しかし、今回の低コスト構成ではEC2とRDSを`ap-northeast-1a`に揃える方針だったため、追加でRDSの配置変更を行うことにした。

ここで理解したのは、**「Single-AZにすること」と「特定のAZに配置すること」は同じ操作ではない**という点である。Multi-AZのStandbyを廃止できたとしても、残ったPrimaryが当初想定したAZに存在するとは限らない。

設定画面の「マルチAZ：なし」という表示だけでは配置先を確認したことにならず、実際のAZも併せて確認する必要があった。

## 2. Multi-AZのフェイルオーバーを配置変更に利用する

今回、Single-AZのRDSについて、管理画面から直接AZを変更する方法は取れなかった。

そこで、一度RDSをMulti-AZ構成へ戻し、`ap-northeast-1a`側にStandbyが作成されたことを確認したうえで、**強制フェイルオーバーによって1a側をPrimaryに切り替える**方法を採用した。その後、再びSingle-AZへ変更した。

この作業を通じて、フェイルオーバーは障害発生時に自動で切り替わる仕組みとしてだけでなく、**稼働系を別のAZへ切り替えるための操作にも利用できる**と学んだ。

ただし、今回はあくまで実際の配置を確認しながら実施した手順である。Multi-AZ化やフェイルオーバーを実行するだけで、確認なしに目的のAZへ移動できたと判断してはいけない。

## 3. 配置変更前のバックアップと変更後の確認

強制フェイルオーバーの前には、RDSの**手動スナップショット**を取得し、利用可能な状態になったことを確認した。

その後、フェイルオーバーによって`ap-northeast-1a`側がPrimaryになったことを確認し、Single-AZへ戻した後にも、以下の状態を確認した。

- マルチAZ：なし
- Availability Zone：`ap-northeast-1a`
- RDSのステータス：利用可能

この確認を行ったことで、単に構成変更の操作が受け付けられたことと、**目的の配置・稼働状態に到達したこと**を区別できた。

また、RDSのステータスが「利用可能」であっても、アプリケーションからデータベースへ正常にアクセスできるとは限らない。そのため、変更後にChinese Output Forgeから問題の追加・削除を行い、読み書きが機能していることも検証した。

## 4. AWSの設定画面だけで移行完了とは判断しない

今回の移行では、Elastic BeanstalkをLoad BalancedからSingle Instanceへ、RDSをMulti-AZからSingle-AZへ変更した。

最終確認では、AWSリソースの状態だけでなく、次の点を確認した。

- `https://chinese-output-forge.com`から独自ドメインでアクセスできること
- アプリケーションの主要機能が動作すること
- データベースへの読み書きができること
- Elastic Beanstalkのヘルスが`Green`であること
- RDSが目的のSingle-AZ構成で稼働していること

**EC2やRDSが稼働していることと、Webアプリケーションが利用できることは同義ではない**。

今回の作業では、ネットワーク、Security Group、DNS、HTTPS、リバースプロキシ、Spring Boot、RDSの各要素がつながって初めて、アプリケーションが利用可能になることを改めて確認できた。

## 5. 高可用性構成を経験したうえで低コスト化した意味

今回の目的は、単にAWSリソースの数を減らすことではなく、Chinese Output Forgeを継続運用しやすい構成に変更することだった。

高可用性構成ではALB、複数AZのEC2、NAT Gateway、Multi-AZ RDSなどを利用していた。これらを一度構築・検証していたため、低コスト化で**どの機能を削減し、どのような可用性を失うのか**を理解したうえで構成を選択できた。

一方、Single InstanceとSingle-AZにしたことで、EC2やRDSの障害に対する冗長性は以前より低くなった。今回の構成は、すべてのサービスに適した構成ではなく、個人開発アプリの運用目的とコストを踏まえた選択である。

## まとめ

今回の追加修正と最終確認から、次の点を学んだ。

- Single-AZ化と配置先AZの変更は区別して考える。
- Multi-AZのフェイルオーバーは、Primaryの配置を切り替える操作としても利用できる。
- 重要な変更の前にはスナップショットを取得し、変更後には目的の状態になったか確認する。
- AWSのリソース状態だけでなく、アプリケーションからの実際の操作で正常性を確かめる。
- 可用性とコストのトレードオフを理解し、運用目的に応じて構成を選ぶ。

これで、AWS高可用性構成から低コスト構成への移行についての学習内容は一区切りとなる。
