# 032-04 AWS低コスト構成④｜CloudWatch・SNSによる監視設定の見直し（学習ログ）

## はじめに

前回の032-03では、Route 53の切り替えとEC2上でのHTTPS構築を通じて、DNS、TLS、nginx、Spring Bootそれぞれの役割を整理した。

今回は、Elastic BeanstalkをSingle Instance環境へ移行した後の監視設定について振り返る。主な学習対象は、**監視対象が変わった場合のCloudWatch Alarmの扱い**と、**CloudWatchとSNSの役割の違い**である。

## 1. 環境を移行しても、既存のアラームが自動的に新EC2を監視するわけではない

高可用性構成で使用していたCloudWatch Alarmは、旧環境のEC2を監視対象としていた。

一方、今回の低コスト構成では、新たに作成したSingle Instance環境のEC2を使用する。アプリケーションの役割は同じでも、**監視対象のEC2インスタンスが変わるため、旧アラームをそのまま使っても新環境の監視にはならない**。

そこで、新EC2の`CPUUtilization`を対象とするCloudWatch Alarmを作成した。

- 監視対象：新しいSingle Instance環境のEC2
- メトリクス：`CPUUtilization`
- 統計：平均CPU使用率
- アラーム条件：CPU使用率が60%以上
- 通知先：既存のSNSトピック`chinese-output-forge-alerts`

今回理解したのは、監視設定は単に「CPUを監視する」という抽象的な設定ではなく、**どのリソースのメトリクスを監視するか**まで含めて成立しているという点である。

## 2. CloudWatch AlarmとSNSは別の役割を担う

今回の構成では、CloudWatchとSNSを組み合わせてCPU負荷の通知を行う。

- **CloudWatch**：EC2のCPU使用率をメトリクスとして監視する。
- **CloudWatch Alarm**：設定した条件を満たすと、アラームの状態を`ALARM`へ変更する。
- **SNS**：アラームからの通知を受け、メールのサブスクリプションへ配信する。

このように、**監視・条件判定と、通知の配信は別の仕組み**である。

今回変更する必要があったのは監視対象のEC2であり、通知先として使用していたSNSトピックは引き続き利用できた。すべての設定を新規作成するのではなく、変更が必要な部分と再利用できる部分を区別して考えることが重要だった。

## 3. 設定の完了と通知の動作確認は区別する

旧環境では、`yes`コマンドで意図的にCPU負荷を発生させ、CloudWatch Alarmの状態遷移とSNSによるメール通知を確認していた。

今回の新環境では、同じ仕組みを利用することから、**新EC2での負荷試験は実施していない**。

したがって、今回記録できる事実は次のとおりである。

- 新EC2を監視対象とするCloudWatch Alarmを作成した。
- 通知先として既存のSNSトピックを設定した。
- 旧環境ではCPU負荷によるアラーム遷移とSNS通知を検証済みだった。
- **新環境でアラームを意図的に発火させる再検証は省略した。**

ここから、**監視設定を作成したことと、その環境で通知が実際に届くことを確認したことは同じではない**と整理できた。

学習ログでも、実施していないテストまで「確認済み」と書かないようにしたい。

## まとめ

今回の監視設定の見直しを通じて、AWS環境を移行するときにはアプリケーションやネットワークだけでなく、**監視がどのリソースを参照しているか**も確認する必要があると分かった。

また、CloudWatch AlarmとSNSの役割を分けて考えることで、監視対象が変わっても通知先を再利用できることを理解した。

一方、今回の新環境では通知の再テストを行っていない。**設定内容と検証済みの範囲を正確に区別して残すこと**も、運用に関する学習の一つだった。
