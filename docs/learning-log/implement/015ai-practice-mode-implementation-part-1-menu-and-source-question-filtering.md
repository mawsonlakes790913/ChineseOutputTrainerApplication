# 015 AI問題生成モードの実装その1 学習ログ

今回はAI問題生成モードその1として、主に以下の機能を実装した。

* AI問題生成メニュー画面
* 理解度・難易度・お気に入り・文法／構造による生成元問題の絞り込み
* 現在の学習対象言語による絞り込み
* `allow_ai_variation`によるAI生成可能問題の絞り込み
* 検索条件に応じたAI生成対象問題数の表示
* AI問題生成に使用する`template`・`subject_type`・`verb_variation`のデータ整備

今回の段階では、AIへ実際に問題生成を依頼する処理までは実装していない。

まず、

```text
ユーザーが条件を指定
    ↓
Questionテーブルから
AI生成元として使用できる問題を絞り込む
    ↓
AI生成対象問題数を表示
```

という、AI問題生成を行う前段階の仕組みを実装した。

AI生成対象問題の検索では、

```text
ユーザーが指定する条件

・理解度
・難易度
・お気に入り
・文法・構造
```

に加えて、

```text
内部で適用する条件

・現在の学習対象言語
・allow_ai_variation = true
```

を使用する。

また、今後AIへ問題生成を依頼するときに備えて、各Questionに設定する`template`などの生成条件についても整理した。

# 1. AIに問題全体を自由に書き換えさせない

今回のAI問題生成では、AIに元の問題をそのまま渡して自由に別の文章へ書き換えさせるのではなく、QuestionをDBへ登録する段階で、変更可能な部分を`template`として定義する。

例えば、

```text
他把手机忘在公司了。
```

という問題であれば、

```text
{subject}把{noun}忘在{noun}了。
```

のようなtemplateを設定できる。

これによってAIは、

```text
{subject}
{noun}
```

の部分を変更できる一方、

```text
把 ～ 忘在 ～ 了
```

という元の問題の骨格は維持する。

つまり、

```text
Question
    ↓
templateで変更可能箇所を定義
    ↓
subject_typeなどで生成条件を追加
    ↓
AIはその範囲内で問題を生成
```

という方式にする。

この方法によって、元のQuestionが持っている文法・構造などの学習ポイントを維持したまま、語彙や状況の異なる問題を生成できるようにする。

# 2. `{predicate}`というパラメータ

`{predicate}`は、**動詞・形容詞のどちらも入り得る述語位置**を表すパラメータとして使用する。

例えば、「越〜越〜」構文では、

```text
越{predicate}越{predicate}
```

のように、`越`の後ろに必ずしも動詞だけが入るとは限らない。

```text
天气越来越冷了。
→ 形容詞「冷」
```

```text
我越想越觉得奇怪。
→ 動詞「想」「觉得」
```

このように、同じ構文上の位置に動詞が入る場合と形容詞が入る場合の両方がある。

そのため、この位置を、

```text
{verb}
```

または、

```text
{adjective}
```

のどちらかに限定するのではなく、

```text
{predicate}
```

として、その文脈に適した述語をAIに生成させるためのパラメータとして扱う。

各パラメータは次のように使い分ける。

| パラメータ           | 用途                  |
| --------------- | ------------------- |
| `{verb}`        | 動詞が入る位置             |
| `{verb_phrase}` | 動詞句が入る位置            |
| `{adjective}`   | 形容詞が入る位置            |
| `{predicate}`   | 動詞・形容詞のどちらも入り得る述語位置 |

このように、templateのパラメータは単純に品詞ごとに分けるのではなく、**その構文上の位置に何が入り得るか**を基準に設定する。

# 3. `verb_variation`は中国語版ではすべて`FIXED`でよい

今回templateを設定する過程で、中国語版では`verb_variation`を基本的にすべて`FIXED`としてよいと考えた。

`verb_variation`は、単純に、

```text
ある動詞
    ↓
別の動詞
```

へ変更してよいかを表すために導入したものではない。

当初は、

```text
時制
完了形
意思の追加
```

などを、原文とは異なる形へ変更してよいか制御する目的で導入した。

例えば英語では、

```text
will
be going to
would
could
```

など、時制や意思を表す要素が動詞や助動詞と強く関係する。

一方、中国語ではこれらの意味は、動詞そのものの活用よりも、時間表現やアスペクトなど、文に付随する要素によって表現されることが多い。

また、必要なアスペクト表現については、

```text
{subject}骑{noun}去{noun}了。
```

のように、templateそのものへ含めることができる。

この場合、

```text
了
```

は変更可能なパラメータではないため、AIが別の形へ変更する必要はない。

そのため、中国語版ではAIにアスペクト表現を自由に変更させる必要性は低く、元のQuestionが持つ文法構造を維持した方がよい。

したがって、中国語版では`{verb}`・`{verb_phrase}`を持つQuestionについても、

```text
verb_variation = FIXED
```

として運用する。

DBでは以下のように設定した。

```sql
UPDATE question
SET verb_variation = 'FIXED'
WHERE template LIKE '%{verb}%'
   OR template LIKE '%{verb_phrase}%';
```

なお、`verb_variation`自体は削除しない。

将来的に英語版などを実装した場合には、時制・相・助動詞などの変更可否を制御する用途として利用できる可能性があるため、中国語版では`FIXED`として運用しながらフィールド自体は残す。

# 4. `subject_type`の設計

`template`内の`{subject}`に対して、AIがどの種類の主語を生成してよいかを`subject_type`で制御する。

## 4-1. `subject_type`の分類

`subject_type`では、以下の3種類を扱う。

| 種類    | 意味                   | 生成例                         |
| ----- | -------------------- | --------------------------- |
| 代名詞   | 人称代名詞を使用する           | `我`、`你`、`他`、`她`、`我们`など      |
| 代名詞以外 | 人物を表す一般的な名詞・名詞句を使用する | `我妈`、`那个孩子`、`我的同事`、`一位老师`など |
| どちらでも | 代名詞・代名詞以外のどちらも使用できる  | `他`、`我的同事`など                |

template側ではこれらを区別せず、主語を変更できる場所をすべて、

```text
{subject}
```

とする。

例えば、

```text
{subject}把{noun}忘在{noun}了。
```

というtemplateの場合、`{subject}`に実際に何を生成してよいかは`subject_type`によって決定する。

このようにすることで、template側で、

```text
{pronoun}
{person}
```

などのパラメータを使い分ける必要がなくなる。

## 4-2. 人名・愛称は生成しない

`subject_type`が「代名詞以外」であっても、**人名や愛称は生成させない**。

例えば、中国語教材では、

```text
小王
老李
小张
小陈
```

のような架空の人物名・呼び方がよく使用される。

また、

```text
王老师
李先生
```

のように、姓によって特定の人物を表す表現もある。

しかし、AI問題生成では、このような人名・姓・愛称に依存した主語は生成しない。

つまり、`subject_type`が「代名詞以外」であっても、

```text
小王
老李
小张
小陈
王老师
李先生
```

などを生成するのではなく、

```text
我妈
我的朋友
我的同事
那个孩子
那个学生
一位老师
公司的员工
```

のような、**一般的な人物を表す名詞・名詞句**を生成する。

これは`NON_PRONOUN`を、

```text
代名詞以外なら何でもよい
```

という意味ではなく、

```text
人名・愛称を使用せず、
一般的な人物名詞・名詞句を使用する
```

というルールで運用することを意味する。

## 4-3. 「代名詞以外」で使用する表現

「代名詞以外」の場合は、人名ではなく、一般的な人物を表す名詞・名詞句を使用する。

例えば、

```text
我妈
我爸爸
我的朋友
我的同事
那个孩子
那个学生
一位老师
公司的员工
```

などである。

例えば、

```text
{subject}工作太忙了，连{verb_phrase}的时间都没有。
```

というtemplateであれば、代名詞を使用して、

```text
她工作太忙了，连吃饭的时间都没有。
```

と生成することもできる。

一方、`subject_type`が代名詞以外であれば、

```text
我的同事工作太忙了，连吃饭的时间都没有。
```

```text
我妈工作太忙了，连休息的时间都没有。
```

```text
那个学生学习太忙了，连运动的时间都没有。
```

のように、人物名を使用せずに主語を変化させることができる。

これによって、

```text
他
她
我
```

などの代名詞ばかりが生成されることを防ぎながら、人名を新しく作ることなく文章に変化を持たせることができる。

## 4-4. `template`と`subject_type`の役割を分ける

例えば、

```text
{subject}坐{noun}去{noun}。
```

というtemplateがあった場合、templateそのものは、

```text
この位置の主語を変更してよい
```

ことだけを表す。

実際にどの種類の主語を生成するかは`subject_type`によって制御する。

### 代名詞の場合

```text
我坐地铁去公司。
他坐公交车去学校。
她坐出租车去机场。
```

### 代名詞以外の場合

```text
我的同事坐地铁去公司。
那个学生坐公交车去学校。
我妈坐出租车去机场。
```

### どちらでもよい場合

上記の両方を生成可能とする。

したがって、

```text
template
    ↓
どこを変更してよいか

subject_type
    ↓
{subject}にどの種類の主語を入れてよいか
```

という役割分担になる。

`template`へ主語の種類まで埋め込まず、変更可能な場所と変更時の条件を別々に管理する。

## 4-5. 人名・愛称を生成しないルールは共通プロンプト側で制御する

`subject_type`の役割は、

```text
代名詞
代名詞以外
両方
```

のどれを使用できるか指定することに限定する。

一方、

```text
人名を生成しない
愛称を生成しない
```

というルールまで各Questionへ個別に保存する必要はない。

これらは、すべてのAI問題生成に共通するルールとして、AIへ送信する**共通プロンプト**で指定する。

概念的には以下のようになる。

```text
{subject} generation rules:

- Do not generate personal names.
- Do not generate nicknames or name-like forms.
- If subject_type is PRONOUN, use an appropriate personal pronoun.
- If subject_type is NON_PRONOUN, use a natural generic noun or noun phrase referring to a person or people.
- If subject_type allows both, either may be used.
```

これによって、例えば`NON_PRONOUN`であれば、

```text
我的同事
那个学生
我妈
一位老师
```

などは生成できるが、

```text
小王
老李
小张
王老师
李先生
```

などは生成しないようにする。

最終的に、それぞれの役割は以下のように分離する。

| 項目             | 役割                                   |
| -------------- | ------------------------------------ |
| `template`     | AIが文中のどこを変更してよいかを指定する                |
| `subject_type` | `{subject}`にどの種類の主語を生成してよいかを指定する     |
| 共通プロンプト        | 人名・愛称を生成しないなど、全Question共通の生成ルールを指定する |

このように、Questionごとに異なる条件はDBに保存し、すべてのQuestionに共通する生成ルールはプロンプト側で管理する。

# 5. AI問題生成時のジャンル指定は今回は実装しない

AI問題生成では、

```text
政治
スポーツ
自然科学
国際問題
```

など、生成する文章のジャンルをユーザーが指定する機能も考えられる。

しかし、今回のAI問題生成では、

```text
人間側で変更可能な部分と
維持すべき部分をあらかじめ定義
    ↓
AIはその範囲内で問題を生成
```

という方式を採用している。

例えば、

```text
下課後，我常和同學一起去圖書館念書。
```

という問題がある。

templateの変更可能部分を置き換えるだけでも、

```text
放學後，我常和朋友一起去咖啡廳念書。
```

```text
午餐後，我常和室友一起去閱覽室念書。
```

```text
打工後，我常和同事一起去咖啡店念書。
```

```text
晚餐後，我常和妹妹一起去書店念書。
```

```text
社團活動後，我常和學長一起去自習室念書。
```

のように、さまざまな文章へ改変できる。

これらは必ずしもすべて「学園生活」という同じジャンルに収まるわけではないが、

```text
私が
    ↓
ある出来事の後に
    ↓
誰かと
    ↓
どこかへ行って
    ↓
勉強する
```

という元の文章の意味上の骨格は維持されている。

一方、ここへ「自然科学」などのジャンルを指定すると、

```text
實驗後，我常和研究員一起去研究室念書。
```

のような文章を作ることはできる。

しかし、これは自然科学に関連する単語を使用しているだけであり、「自然科学そのものについて述べた文章」になっているわけではない。

同様に「国際問題」を指定して、

```text
國際會議後，我常和同事一起去資料室念書。
```

としても、国際問題に関連する単語を使用しただけで、元の文章の意味上の骨格は変わっていない。

ジャンルへ強く適合させるためには、変更可能な単語だけではなく、元の文章の意味上の骨格そのものを変更する必要がある。

しかし、それを許可すると今回採用している、

```text
人間が変更可能箇所を定義
    ↓
AIはその範囲内だけを変更
```

という生成方式から外れてしまう。

ジャンル指定を実現するのであれば、例えばQuestion自体にジャンル情報を持たせ、

```text
ユーザーがジャンルを指定
    ↓
そのジャンルに適した
生成元QuestionをDBから取得
    ↓
そのQuestionのtemplateを使って生成
```

とするなど、生成元Questionを選択する段階でジャンルを利用する方法が考えられる。

そのため、**AI問題生成時にジャンルを指定する機能については、現バージョンでは実装を見送ることにした。**

# 6. 今回の実装を通して

今回の実装では、AIへ実際にリクエストを送る処理に入る前に、

```text
Questionを検索する条件

        と

AIがQuestionを変更する条件
```

を分けて整理した。

ユーザーが指定するのは、

```text
理解度
難易度
お気に入り
文法・構造
```

といった「どの問題を練習するか」に関する条件である。

一方、

```text
template
subject_type
verb_variation
共通プロンプト
```

などは、「選択された問題をAIがどのように変更するか」をアプリケーション側で制御するために使用する。

特に`template`については、

```text
AIに元の文章を渡して
自由に書き換えさせる
```

のではなく、

```text
人間
    ↓
変更可能な部分をtemplateとして定義

AI
    ↓
定義された部分だけを変更
```

という役割分担にする。

さらに、

```text
template
    → どこを変更してよいか

subject_type
    → {subject}に何を入れてよいか

verb_variation
    → 動詞に関する変更条件

共通プロンプト
    → 人名・愛称を生成しないなどの共通ルール
```

と、AI生成に関する条件についても役割を分ける。

したがって、AI問題生成全体としては、

```text
ユーザー
    ↓
練習したい問題の条件を指定
    ↓
DB
    ↓
生成元Questionを取得
    ↓
template / subject_type / verb_variation
などの生成条件を取得
    ↓
共通プロンプトと組み合わせる
    ↓
AI
    ↓
元の学習ポイントを維持した問題を生成
```

という流れになる。

今回の段階で、AI問題生成の前提となる生成元Questionの絞り込みと、AIにどこまで問題を変更させるかという基本方針を整理できた。
