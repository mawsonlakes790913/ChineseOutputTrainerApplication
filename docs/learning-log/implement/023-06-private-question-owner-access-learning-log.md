# 023-06 所有者付き非公開問題へのアクセス制限 — 学習ログ

## はじめに

本章では、開発者自身が利用する非公開問題を追加した際に判明したアクセス制御の問題を振り返る。焦点はSQLの修正手順ではなく、**データの属性をどの目的で使うべきか**、そして**アプリケーション内の複数の取得経路に同じアクセス規則を適用する必要性**にある。具体的なRepositoryの変更内容と動作確認は、実装ログ「023-06 所有者付き非公開問題へのアクセス制限」に記録した。

## 1. 問題の生成元と公開範囲は異なる概念

従来は、`ai_generated = false`の問題を共通問題として扱い、`ai_generated = true`の場合にのみ所有者を確認する検索条件が存在していた。この設計は、AI生成問題だけが個人に紐づくという前提では成立していた。しかし、開発者用に`ai_generated = false`かつ`owner_user_id`を持つ問題を追加すると、他のユーザーにも取得され得ることが分かった。

ここで整理すべきなのは、各カラムが表す意味である。

- `ai_generated`：問題がAI生成由来かどうか
- `allow_ai_variation`：AI問題生成の元として利用できるかどうか
- `owner_user_id`：問題の所有者が存在するか、存在する場合は誰か

これらは互いに独立した属性である。特に、**「AI生成ではない」ことは「全ユーザーに公開されている」ことを意味しない**。生成方法に基づいてアクセス権限を判断していたことが、今回の問題の原因だった。

修正後は、`owner_user_id IS NULL`を共通問題、`owner_user_id = :userId`を本人の所有する問題として扱う。問題の生成元を絞り込む条件と、問題へのアクセスを許可する条件を区別して考えることが重要だと理解した。

## 2. 画面の非表示とデータへのアクセス制御は別物

他人の非公開問題を問題一覧に表示しないだけでは、アクセス制御として不十分である。アプリには通常学習、未学習問題、復習、ユーザー用問題一覧など、問題を取得する複数の経路が存在する。さらに、評価やお気に入り登録では問題IDを直接指定して操作する。

例えば、一覧から非公開問題が消えていても、IDを指定した評価処理がその問題を許可してしまえば、一覧表示の制限だけでは守れない。今回、`existsAccessibleQuestion(...)`の判定も`aiGenerated`ではなく所有者情報に基づく条件へ変更したのは、そのためである。

この作業から、**アクセス制御は「何を表示するか」というUIの問題ではなく、「誰がどのデータを取得・操作できるか」というデータアクセスの問題**だと理解した。画面ごとに対処するのではなく、Repositoryの取得条件や操作前のアクセスチェックにまで規則を反映させる必要がある。

また、通常学習では問題の件数取得と実際の問題取得の両方に同じ制限を適用した。片方だけ修正すると、画面に表示される件数と実際の出題対象が一致しなくなる。検索条件を変更する際は、関連する集計処理との整合性も確認しなければならない。

## 3. 既存の検索条件を維持しながら権限を追加する

ログインユーザーの通常学習には、`ALL`、`ORIGINAL_ONLY`、`GENERATED_ONLY`という出題元の絞り込み条件がすでにあった。今回の修正では、これらの機能を残したまま所有者による制限を追加する必要があった。

設計上は、所有者の条件を共通部分としてまとめ、出題元の条件と分離する書き方も可能である。一方、実装では既存SQLとの差分を追いやすくするため、元の分岐構造を残して各条件へ所有者判定を追加した。

ここから、SQLを短くすることが常に最優先とは限らないと分かった。既存の振る舞いを維持する変更では、**条件の意味を明確にしつつ、変更箇所を検証しやすくすること**にも価値がある。ただし、同じ所有者条件が複数の分岐に現れるため、将来変更するときは適用漏れに注意が必要である。

復習処理についても、通常学習とは別に`study_history`と`question`を結合して取得するため、独立したアクセス制限が必要だった。通常学習で問題を取得できないことだけをもって、復習からも取得できないと判断してはいけない。

## 4. 管理者権限と一般ユーザーの利用範囲を分ける

一般ユーザー向けの問題一覧では、共通問題と本人が所有する問題だけを取得する。一方、Admin用の問題一覧は、所有者を問わず全問題を管理する用途であり、同じ制限を適用しなかった。

これは、同じ`question`テーブルを扱っていても、利用者の役割と操作の目的によって許可範囲が異なるためである。**アクセス条件を全クエリに機械的に追加するのではなく、その処理が誰のためのものかを確認する**必要がある。

また、開発者専用の非公開問題のために新しい学習モードや検索条件は設けなかった。所有者本人には通常の問題として利用できるようにし、特定の問題を選んで学習したい場合は既存の問題リスト機能を活用する。内部的なデータ管理の要件を満たすために、一般ユーザー向けUIまで複雑にする必要はないという判断である。

## まとめ

今回の修正で最も重要だったのは、`ai_generated`と`owner_user_id`を別々の責務を持つ属性として扱い直したことだった。そこから、通常学習・復習・一覧表示・評価・お気に入り登録など、問題にアクセスする経路を横断して確認する必要性が見えてきた。

実装ログでは、開発者が所有する非AI問題を追加した後、所有者本人には表示され、別のユーザーには表示されないことを件数と一覧で確認している。ただし、問題IDを直接指定する操作や、復習に異常な履歴が含まれる場合の個別テストまで実施した証拠ではない。**実装した制御の範囲と、実際に検証できた範囲を区別すること**も、今回の振り返りで意識すべき点である。
