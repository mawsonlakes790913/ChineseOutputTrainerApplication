# 031-05 AWS高可用性構成⑤｜独自ドメイン・HTTPS・監視通知の構築（学習ログ）

この章では、独自ドメインの取得とDNS設定、HTTPS通信の構築、CloudWatchとAmazon SNSによる監視通知を通して学んだことを記録する。実際のAWS設定、コマンド、テストの経過については対応する実装ログ031-05を参照する。

## Route 53と独自ドメインの管理

当初はRoute 53でドメイン自体も取得する予定だったが、AWS側で登録できず、問い合わせても作業を進められなかったため、お名前.comで`chinese-output-forge.com`を取得する方法へ変更した。

この過程で、**ドメインの登録事業者（Registrar）とDNSの管理先は同じである必要がない**ことを理解した。

ドメインの契約・更新はお名前.comで行いながら、ネームサーバーをRoute 53のものに変更すれば、DNSレコードはRoute 53で管理できる。

また、Route 53にHosted Zoneを作成しただけではDNSの管理先は切り替わらない。ドメイン登録事業者側でもネームサーバーを変更する必要がある。`dig`でGMOのネームサーバーからAWSのネームサーバーへ切り替わる過程を確認したことで、この違いを具体的に理解できた。

## Route 53 AliasとALB

AWSの学習教材には、AレコードをEC2のIPアドレスへ向ける例もあった。しかし、今回の構成ではEC2をPrivate Subnetに配置し、外部からのアクセスはALBで受ける設計としていた。

そのため、教材の手順をそのまま使用せず、Route 53のAレコードをAliasとしてALBへ向けた。

ここから、教材と実際の構成が異なる場合は、操作手順をそのまま再現するのではなく、**ユーザーからの通信を最初に受けるAWSリソースは何か**を考えた上でDNSの接続先を決める必要があると学んだ。

また、ALBのIPアドレスを固定値として通常のAレコードに記載するのではなく、Route 53のAliasによってALBを接続先として指定できることも理解した。

## ACMとHTTPS通信の切り分け

Route 53からALBへのルーティングを設定した直後、ドメインだけを入力してアクセスすると接続できなかったが、`http://`を明示すると正常に表示された。

この結果から、DNSの名前解決とALBへのルーティングは機能しており、HTTPS側が未構築であると切り分けることができた。

その後、ACMで証明書を発行し、Route 53によるDNS検証を行い、ALBにHTTPSの443番リスナーを追加した。しかし、それでもHTTPSアクセスはタイムアウトした。

原因は、**ALBのSecurity Groupで443番ポートのインバウンド通信を許可していなかったこと**だった。

この経験から、HTTPS通信にはDNSの設定、証明書、ALBのHTTPSリスナー、Security Groupによる通信許可など、複数の設定が関係することを理解した。証明書を発行するだけではHTTPS通信は成立しない。

また、接続できないときはすべてを一度に疑うのではなく、HTTPでは接続できるか、HTTPSリスナーは存在するか、443番ポートは許可されているかというように、確認対象を分けることが重要だと学んだ。

## CloudWatchとAmazon SNSの監視通知

CloudWatch AlarmとSNSを設定しただけでは、実際に異常が起きたときにメール通知まで届くかどうかは分からない。そのため、EC2に意図的にCPU負荷を発生させ、通知経路を通して確認した。

`nproc`で2 vCPUであることを確認した上で、`yes > /dev/null &`を2つ実行してCPU使用率を上げた。その結果、CloudWatch Alarmが`ALARM`状態へ遷移し、SNSを経由してメールが届いた。

この経験から、**監視は設定したことだけでなく、想定した異常条件で通知が届くことまで確認する必要がある**と学んだ。

また、負荷テスト後には`ps aux | grep yes`でプロセスIDを確認し、負荷を発生させたプロセスを停止した。テストでは異常状態を作るだけでなく、終了後に正常な状態へ戻すことも必要である。

## この章で学んだこと

独自ドメイン、HTTPS、監視通知はいずれも、単一のAWSサービスだけで完結する設定ではなかった。

特に今回の作業では、ドメイン登録とDNS管理、名前解決とHTTPS接続、監視条件と通知配信をそれぞれ区別することで、問題が起きた際に原因を切り分けられるようになった。

次の031-06では、ここまで構築した各サービスが個別に存在するだけでなく、アプリケーション全体として想定した通信経路で動作しているかを確認した際の学びを整理する。
