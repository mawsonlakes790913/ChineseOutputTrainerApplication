# 032-01 AWS低コスト構成①｜移行計画とRDSのSingle-AZ化（学習ログ）

## はじめに

Chinese Output Forgeを高可用性構成から低コスト構成へ移行する際に、構成を変更した理由、事前の棚卸し、RDSのSingle-AZ化を通じて理解したことを振り返る。

具体的なAWSコンソールでの操作、設定値、スクリーンショットについては、対応する[032-01の実装ログ](./032-01-aws-low-cost-plan-rds-single-az-implementation-log.md)に記録している。

## 1. 高可用性は常に最適とは限らない

高可用性構成では、ALB、複数AZのEC2、Auto Scaling、各AZのNAT Gateway、Multi-AZ RDSを組み合わせた。これは障害への耐性を学ぶには有用だったが、個人開発の中国語学習アプリで常時維持するには運用コストが大きい。

**高可用性を実現できることと、現在のサービスにその可用性が必要であることは別問題**である。今回は一度高可用性構成を構築・検証したうえで、継続運用に適した構成へ縮小する判断をした。

## 2. 構成変更によって通信経路が変わる

- 高可用性構成では、Route 53で名前解決した後、クライアントはALBへ接続し、ALBがPrivate SubnetのEC2へリクエストを振り分けていた。
- 低コスト構成ではALBを廃止し、Public Subnetに配置した1台のEC2がElastic IPを通じてアクセスを受ける。
- EC2がInternet Gatewayを利用して直接インターネットへ通信できるため、Private SubnetのEC2向けに用意していたNAT Gatewayは不要になる。
- RDSはSingle-AZにするが、DB Subnet Groupのために異なるAZのPrivate DB Subnetを残す。**サブネットが残っていることと、そこに稼働中のDBが存在することは同義ではない**。

Route 53はDNSによる名前解決を担当する。DNSでElastic IPが返された後のHTTPS通信はRoute 53を経由せず、クライアントとEC2の間で行われる点も整理できた。

## 3. 最初の設計をそのまま実行しない

当初は既存の`10.1.20.0/24`をPublic Subnetに変更する予定だったが、実際には移行中も旧EC2が利用していた。そのため、新しいPublic Subnetとして`10.1.12.0/24`を作成し、新旧環境を並行稼働させる方法へ変更した。

**設計図は最終的な到達点を示すものであり、移行途中の安全な手順まで保証するものではない**。既存環境の依存関係を考慮して手順を修正する必要があった。

## 4. 変更前にAWSリソースの依存関係を棚卸しする

ALB、EC2、NAT Gateway、RDSを個別に削除・変更すると、どのSecurity GroupやRoute Tableが使われているのか分からなくなるおそれがあった。そのため、移行前にSubnet、Route Table、Security Group、AWSリソース、Spring Bootの環境設定を表に整理した。

棚卸しでは「変更」「維持」「削除」を区別した。

- Public SubnetとPrivate Subnetの違いは名前ではなく、関連付けられたRoute Tableなどのネットワーク設定によって決まる。
- EC2用Security Groupは、旧環境ではALBからのアプリケーション通信を許可していたが、新環境ではインターネットからのHTTP・HTTPSを考慮して設計し直す必要がある。
- RDS用Security Groupは基本的に維持できるが、新しいEC2のSecurity Groupを接続元として追加しなければならない。
- CloudWatchとSNSは引き続き利用するものの、監視対象のEC2インスタンスIDが変わるため、アラームは見直す必要がある。

AWSの構成変更では、単にリソースの台数を減らすのではなく、**リソース間の参照関係を更新する作業**が重要だと分かった。

## 5. RDSのSingle-AZ化で想定と実際の配置が異なった

Multi-AZではPrimaryに障害が発生した場合にStandbyへフェイルオーバーできるが、Standbyを維持する分のコストがかかる。今回はランニングコストを優先し、Single-AZへ変更した。

当初は`ap-northeast-1a`側にRDSを残す予定だった。しかし、Single-AZ化後に確認すると、RDSは`ap-northeast-1c`の`10.1.31.0/24`に配置されていた。

RDSの設定画面だけでなく、ネットワークインターフェイスとSubnet IDも確認したことで、**論理的なDB構成と実際のAZ・サブネット配置を区別して確認する必要がある**と理解した。

この段階では実際の配置に合わせ、1cをRDS稼働用、1aをDB Subnet Group維持用の予備として扱うよう計画を修正した。最終的なAZ統一は後の追加修正で行った。

## 6. インフラの変更結果はアプリケーションからも確認する

RDSのステータスが`利用可能`であることだけでは、アプリケーションが正常に使えるとは限らない。ログイン、問題一覧の取得、問題の追加、再読み込み後のデータ保持まで確認した。

**インフラの変更が成功したかどうかは、AWSの設定画面だけでなく、アプリケーションからの読み書きでも判断する**必要がある。

## 振り返り

今回の作業では、高可用性構成のリソースを単純に減らすのではなく、移行途中の通信経路や依存関係を考慮して計画を修正した。また、RDSのSingle-AZ化では、設定変更後の実際の配置先が想定と異なることを確認し、その結果に合わせて構成を見直した。

構成変更の判断、AWS上での実際の配置確認、アプリケーションを使った動作確認を分けて考えることが重要だと学んだ。
