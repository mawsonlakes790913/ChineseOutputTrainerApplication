# 023-08 AI問題生成中のローディング表示 — 学習ログ

## はじめに

AI問題生成では、フォーム送信から結果画面への遷移まで待機時間が生じる。処理そのものが正常でも、画面に変化がなければ利用者には送信されたかどうかが分からない。今回は、処理中の状態を伝えるUIと、画面をまたいで利用するCSSの管理について理解を整理する。

## 1. 処理の完了だけでなく、待機中の状態もUIの一部

AI問題生成はサーバー側で時間を要するため、フォーム送信直後に結果を表示できない。そこで、送信時にローディングオーバーレイを表示し、処理を受け付けたことを視覚的に伝えるようにした。

ここで重要なのは、**処理が進んでいることと、利用者が処理中だと認識できることは別**だという点である。待機表示がなければ、利用者は操作が反映されていないと考え、再送信してしまう可能性がある。

今回の表示は進捗率を示すものではない。スピナーと「Loading...」によって待機状態を知らせるものであり、実際の生成処理の進み具合を計測しているわけではない。

## 2. HTML・CSS・JavaScriptを組み合わせた状態の切り替え

オーバーレイは、それぞれの技術に役割を分けて実装した。

- **HTML**：待機表示の領域とスピナーをあらかじめ用意する。
- **CSS**：`position: fixed`と`inset: 0`で表示領域を覆い、Flexboxで中央に配置する。`z-index`で他の要素より前面に表示する。
- **JavaScript**：フォームの`submit`イベントを受け取り、`d-none`を取り除いて表示する。

今回、CSSには`.loading-overlay { display: flex; }`と`.loading-overlay.d-none { display: none; }`の両方を定義した。**表示用のスタイルと非表示用のスタイルが競合し得る**ため、非表示状態を確実に適用する必要があることも確認した。

対象フォームは`/ai-practice/start`と`/ai-practice/list/start`の2種類である。生成元の選び方が異なっても、同じ待機表示を適用できるようにした。

## 3. 通常のフォーム送信と非同期処理の違い

今回のJavaScriptは、AI生成APIを`fetch`などで直接呼び出して完了を監視するものではない。**通常のフォーム送信をきっかけに表示を切り替え、その後のサーバーレスポンスによる画面遷移に任せる**構成である。

そのため、JavaScriptに生成完了時のオーバーレイ解除処理は追加していない。実装記録で確認したのは、生成開始後に待機表示が現れることまでであり、送信中断などで同じ画面に残った場合の復帰処理は今回の対象外である。

この違いから、ローディング表示を設計する際には、**送信後にページが遷移するのか、同じページ内で非同期に結果を受け取るのか**を先に把握する必要があると分かった。

## 4. 共通CSSは作成元ではなく役割で管理する

ローディング表示の追加時、AI生成メニューが`/css/review/menu.css`を読み込んでいることに気付いた。そこには復習専用ではなく、文法・構造一覧の折り畳みやツールチップに関するスタイルが定義されていた。

このスタイルは復習メニューとAI生成メニューの両方で使用しているため、`/css/common/question-structure.css`へ移した。

最初に実装した画面の名前をそのまま共通スタイルの置き場所にすると、別画面から見たときに依存関係が分かりにくくなる。**複数画面で共有するCSSは、そのスタイルが何を表現するかに基づいて命名・配置する**方が、後から利用箇所を把握しやすい。

## まとめ

今回の学習の中心は、AI生成ロジックの変更ではなく、待機時間のある処理を利用者にどう伝えるかというUI設計だった。また、HTML・CSS・JavaScriptの役割分担、通常のフォーム送信に伴う画面遷移、共通スタイルの責務に応じた整理を理解できた。

ローディング表示は小さな追加機能だが、**処理中の状態を明示することもアプリケーションの操作性を構成する重要な要素**である。
