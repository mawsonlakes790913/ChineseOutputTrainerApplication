# 023-10 会員登録完了メールの送信機能 — 学習ログ

## はじめに

会員登録完了メールの追加を通じて、単にメールを送信する方法だけでなく、**ユーザー登録という主処理と、完了通知という付随処理をどう切り分けるか**を考えた。ここでは実装手順の再掲を避け、処理の責務、失敗時の扱い、例外設計、実装順序から得た知見を整理する。

## 1. 登録完了通知と本人確認は異なる機能

今回のメールは、登録したメールアドレスへ会員登録の完了を知らせる通知であり、メールアドレスの所有確認やアカウント有効化を行う仕組みではない。メールにログインIDとログイン画面のURLを記載していても、それだけで本人確認が完了したことにはならない。

通知の目的を明確にしたことで、メールの送信結果を会員登録の成立条件にはしない方針を採った。**通知が届いたかどうかと、アカウントが登録されたかどうかは別の状態**として考える必要がある。

## 2. DBへの登録とメール送信は、成功・失敗を分けて考える

会員登録処理の正常終了後にメール送信を試みる構成では、登録が成功していても、メール作成や送信だけが失敗する可能性がある。

このときメール送信の例外をそのまま画面へ伝えると、ユーザーは登録全体が失敗したと誤解し、再登録を試みるかもしれない。しかし、すでにユーザー情報が保存されていれば、ログインIDやメールアドレスの重複エラーにつながる。

そこで、登録処理の正常終了後に通知を試行し、通知失敗時にはログを残して登録完了の画面遷移を継続するようにした。これは**主処理の結果を、付随する通知処理の失敗で覆さない**ための設計である。

ただし、実装記録から分かるのは登録メソッドの正常終了後に送信を呼び出していることまでであり、DBトランザクションのコミット時点や、すべての送信障害で同じ結果になることまで確認できたわけではない。

## 3. 専用例外を使って失敗の意味を伝える

当初はメール処理の失敗に汎用的な`RuntimeException`を使用していたが、その後`MailSendException`を導入した。

専用例外を使うと、`SignupController`ではメール送信に関係する失敗を意図して捕捉できる。また、元の例外を`cause`として保持すれば、ログから原因を調査する手掛かりも残せる。例外クラスは単にエラーを投げるためではなく、**呼び出し元へ失敗の種類を伝えるための設計要素**でもある。

一方、実装当時のコードでは`MessagingException`を捕捉して`MailSendException`へ変換していた。`JavaMailSender.send()`で発生し得る例外をすべて同じように変換できるとは限らないため、専用例外を用意しただけで全送信失敗を捕捉できると考えてはいけない。この点は例外の発生箇所と型を確認する必要がある。

## 4. 既存機能の再利用と、実装時点の区別

メールアドレスの登録・管理は第27章、`JavaMailSender`によるパスワード再設定メールの送信は第28章で実装していた。会員登録完了メールは、その既存の送信機構を後から再利用して追加した機能である。

そのため、会員登録メールの実装に合わせて新しい送信基盤を作る必要はなかった。一方、通知の目的や送信失敗時の扱いはパスワード再設定メールと同一ではない。**共通の送信手段を再利用しても、各機能の業務上の役割まで同一視しない**ことが重要だった。

また、この節のコードは実装当時のGmail SMTP・`JavaMailSender`方式であり、その後、第33章でAWS SDKを用いたAmazon SES API方式へ変更している。学習ログでは、現在の実装と過去の実装を混同しないよう区別する。

## まとめ

今回の学習で重要だったのは、メール送信APIの呼び出し方よりも、**会員登録と通知の責務を分離し、それぞれの失敗がユーザーにどう見えるかを考えること**だった。

登録完了メールの受信からログインまでの正常系は確認している。一方、送信失敗を意図的に発生させたテスト結果は元の記録にないため、失敗時の挙動を検証済みとは扱わない。
