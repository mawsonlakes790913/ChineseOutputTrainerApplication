# 005 通常学習の実装 その2 - Learning Log

## 1. 要件変更は実装だけでなく関連ドキュメント全体に影響する

今回、通常学習の解答画面に拼音・注音を表示する機能を追加することになり、以下のドキュメントを見直した。

- `requirements.md`
- `data-design.md`
- `er-diagram.md`
- `table-definition.md`
- `screen-design.md`

発音記号を追加するだけの比較的小さな変更に見えたが、実際には要件、データ構造、テーブル、ER図、画面設計まで影響した。

この程度の変更でも複数のドキュメントを修正する必要があり、設計書を実装と同期させ続けることの大変さを実感した。

### 既存ドキュメントを書き換えず「追記」した

今回は既存の記述を直接書き換えるのではなく、各ドキュメントの末尾に変更内容を追記した。

これは単に修正するだけでは、

> 最初からこの仕様だったのか、それとも開発途中で仕様変更されたのか

が分からなくなるためである。

追記として残すことで、

```text
当初の設計
    ↓
実装・検討
    ↓
要件の見直し
    ↓
仕様変更
```

という経緯を後から確認できる。

完成した仕様だけでなく、どの段階で設計を変更したのかを残すことも開発ドキュメントでは重要だと感じた。

## 2. 既存データがあるテーブルへNOT NULLカラムを追加するときの注意

`Question` に拼音と注音を追加した。

```java
@Column(name = "pinyin", columnDefinition = "TEXT")
private String pinyin;

@Column(name = "zhuyin", columnDefinition = "TEXT")
private String zhuyin;
```

この段階では、あえて `nullable = false` を設定しなかった。

既に `question` テーブルには問題データが存在しており、それらのレコードは当然 `pinyin` と `zhuyin` を持っていない。

その状態で最初から、

```java
@Column(name = "pinyin", nullable = false)
```

としてしまうと、既存データとの整合性に問題が発生する可能性がある。

そこで今回は、

```text
① NULL可でカラムを追加
        ↓
② 既存データに拼音・注音をUPDATE
        ↓
③ NULLのデータが残っていないことを確認
        ↓
④ nullable = false に変更
```

という順番で対応した。

### 「全部入力した」ではなく「NULLが存在しない」を確認する

ここで重要だったのは、

> すべての問題に拼音と注音を入力したつもりである

ことを確認するのではなく、

> DB上に実際にNULLが残っていない

ことを確認することである。

そのため、以下のSQLを使用した。

```sql
SELECT COUNT(*)
FROM question
WHERE pinyin IS NULL
   OR zhuyin IS NULL;
```

結果が `0` であることを確認してから `nullable = false` に変更した。

DBの制約を強くする場合、人間の作業結果を信用するのではなく、DBに問い合わせて条件を満たしていることを確認してから制約を追加する方が安全である。

## 3. 拼音・注音の表示切り替えは既存機能を応用できた

発音表記の切り替えは、以前実装した学習対象言語の切り替えと似た構造で実装できた。

```text
設定画面
    ↓
PronunciationTypeController
    ↓
Sessionに設定を保存
    ↓
問題表示時にSessionを参照
    ↓
表示内容を切り替える
```

`PronunciationType` は、

```java
public enum PronunciationType {

    PINYIN,
    ZHUYIN,
    NONE
}
```

とした。

既にSessionを利用した設定変更を実装していたため、今回の仕組みそのものはそれほど難しくなかった。

一度実装した設計パターンを別の機能にも応用できるようになると、似た機能の実装コストを大きく下げられることを実感した。

## 4. 「発音記号を表示しない」という選択肢

当初は拼音と注音の切り替えを考えていたが、最終的には、

```text
PINYIN
ZHUYIN
NONE
```

の3種類とした。

中国語がある程度上達すると、拼音や注音を常に表示することがかえって目障りになる場合がある。

発音表記の助けが必要ないユーザーのために、単に「どちらを表示するか」だけではなく、

> 発音表記そのものを表示しない

という選択肢も必要だと判断した。

学習支援機能は、多ければ多いほど良いわけではない。

習熟度によっては補助情報を減らせることも重要である。

---

## 5. 普通話でも注音を選択可能にした理由

実際の中国語学習環境を考えると、普通話学習者の多くは拼音を使用し、注音を使用することはほとんどない。

そのため現実に合わせれば、

```text
普通話
├── 拼音
└── 表示なし

國語
├── 拼音
├── 注音
└── 表示なし
```

という仕様も考えられる。

しかし今回は、

```text
普通話
├── 拼音
├── 注音
└── 表示なし

國語
├── 拼音
├── 注音
└── 表示なし
```

とした。

理由の一つは、実装難易度にほとんど差がないことである。

また、中国語の事情を知らない利用者や開発者が設定画面を見た場合、

> なぜ普通話だけ選択肢が少ないのか

という不要な疑問を持つ可能性がある。

実際の利用習慣だけを厳密に再現するのではなく、UIの一貫性や実装の単純さも含めて仕様を決定する必要があると考えた。

## 6. 現在の設定画面は暫定実装

現在の `PronunciationTypeController` の役割は非常に単純である。

ユーザーが選択した、

```text
PINYIN
ZHUYIN
NONE
```

のいずれかをSessionへ保存するだけである。

`settings.html` も、

```text
[ 拼音 ] [ 注音 ] [ 表示なし ]
```

から1つを選択すると、その時点でGETリクエストを送り設定を変更する単純な構造になっている。

ただし、これは暫定的な設定画面である。

今後設定項目が増えれば、

```text
設定

Aの設定      [ ... ]
Bの設定      [ ... ]
Cの設定      [ ... ]

発音記号
○ 拼音
○ 注音
○ 表示なし

        [ 適用 ]
```

のように、複数の設定を変更してからまとめて適用するUIへ変更する可能性がある。

現在必要な機能だけを先に実装し、将来必要になるかもしれない複雑な設定画面を最初から作らないことにした。

## 7. 本来は漢字と発音記号を対応させて表示したい

現在の発音表記には改善の余地がある。

理想としては、日本語のルビのように、それぞれの漢字と対応する発音を近い位置に表示したい。

しかし拼音は漢字より表示幅が大きい。

例えば、

```text
我们每天都去公园散步。
Wǒmen měitiān dōu qù gōngyuán sànbù.
```

のように表示すると、中国語本文と拼音の位置が一致しない。

さらに、

```text
想象墙上的画像像窗上的霜。
Xiǎngxiàng qiáng shàng de huàxiàng xiàng chuāng shàng de shuāng.
```

のような文章では、どの拼音がどの漢字・単語に対応しているのか、ぱっと見ただけでは分かりにくくなる。

### ルビ表示の問題

HTMLのRubyタグなどを利用すれば、漢字の上に発音を表示すること自体は可能である。

しかし現在のDBでは、

```text
Question ID = 1

chinese_text
我们坐出租车去车站吧。

pinyin
Wǒmen zuò chūzūchē qù chēzhàn ba.
```

という形で文章全体をそれぞれ保存している。

つまりDB上では、

```text
我们 ↔ Wǒmen
坐   ↔ zuò
出租车 ↔ chūzūchē
```

という文字・単語単位の対応関係を保持していない。

そのため、現在のデータだけから正確なRuby構造を生成することは難しい。

さらに拼音は漢字より横幅が広いため、無理に各漢字へ対応させると、

```text
Wǒmen měitiān dōu qù gōngyuán sànbù.
我 们  每  天   都  去  公  园   散 步。
```

のように中国語本文側の文字間隔まで広がり、かえって読みにくくなる可能性がある。

### 注音ではさらに複雑になる

注音にも同様の問題がある。

加えて、注音は本来、漢字一字の右側に縦方向で配置される形式もあるため、それを正確に再現しようとすると拼音以上に表示処理が複雑になる。

正確な対応表示を実現するには、

```text
漢字・語
    ↕
対応する拼音
    ↕
対応する注音
```

という文字または音節単位のデータ構造が必要になる。

これはDB設計そのものの見直しにつながるため、現段階では導入しないことにした。

`pinyin` と `zhuyin` は自然な文章形式のままDBへ保存し、中国語本文とは別の行として表示する。

## 8. 「最高の仕様」ではなく「現時点で最善の仕様」を選ぶ

発音記号を文字単位で完全に対応させる方が、学習ツールとしては理想に近い。

しかし、それを実現するために、

- DB構造を変更する
- 既存データを文字・音節単位に分解する
- 拼音と漢字の対応情報を保持する
- 注音の配置にも対応する
- 表示ロジックを大幅に複雑化する

必要がある。

現在の開発段階でそこまで実装する価値があるかを考えると、コストが大きすぎる。

そのため、

> 最良・最高の方法ではないが、実装コスト・保守性・現在の目的を考えると最善の方法

として、文章全体の発音表記をそのまま表示する方式を採用した。

今回特に印象に残ったのは、

**理論上もっと優れた方法が存在することと、その方法を実際のアプリへ採用すべきことは別問題である**

という点だった。

## 9. 別解の発音表記を見落としていた

本解答への拼音・注音表示を実装した後で、

> 別解にも発音記号が必要

ということに気づいた。

そのため、

```text
alternative_answer
alternative_answer_pinyin
alternative_answer_zhuyin
```

を持たせる必要が生じた。

拼音・注音対応のために複数の要件・設計ドキュメントを見直した直後だったため、再び関連ドキュメントを確認することになった。

### 見落とした原因

今回の初期データでは、開発を進めるために問題データを先に投入していたが、多くを、

```text
別解なし
条件なし
```

の状態で作成していた。

その結果、通常学習画面の発音表記を設計した際にも、主に `chinese_text` だけを見てしまい、`alternative_answer` の存在を十分考慮できていなかった。

これはテストデータの内容が設計時の視点にも影響する例だと感じた。

今後フィールドを追加するときは、そのフィールドだけを見るのではなく、

```text
この情報と同じ性質を持つ別のデータはないか
```

を確認した方がよい。

今回なら、

```text
本解答に発音が必要
        ↓
別解にも発音が必要ではないか？
```

まで考える必要があった。

## 10. Sessionの値とローカル変数は別物

`/practice/menu` で、Sessionの `languageVariant` が未設定の場合に問題数が0件になる問題があった。

そのため、

```java
LanguageVariant languageVariant =
        (LanguageVariant) session.getAttribute("languageVariant");

if (languageVariant == null) {
    languageVariant = LanguageVariant.MAINLAND;
}
```

として、未設定の場合は `MAINLAND` として扱うよう修正した。

これによって `/practice/menu` は正常に動作した。

しかしその後、発音表記を注音へ変更して通常学習を開始すると、`GET /practice/start` で再びエラーが発生した。

### 原因

上記の処理で変更しているのは、

```java
languageVariant
```

というローカル変数である。

Sessionそのものを書き換えているわけではない。

つまり、

```text
Session
languageVariant = null

        ↓

getPracticeMenu()

ローカル変数
languageVariant = MAINLAND

        ↓

問題数取得成功

        ↓

Session
languageVariant = null
```

である。

その後 `/practice/start` という別のリクエストが発生すると、再びSessionから値を取得する。

```text
/practice/menu
    ↓
nullをMAINLANDとして扱う
    ↓
正常表示
    ↓
/practice/start
    ↓
SessionからlanguageVariantを取得
    ↓
依然としてnull
    ↓
エラー
```

そこで `/practice/start` でも、

```java
LanguageVariant languageVariant =
        (LanguageVariant) session.getAttribute("languageVariant");

if (languageVariant == null) {
    languageVariant = LanguageVariant.MAINLAND;
}
```

とする必要があった。

## 11. 「デフォルトとして扱う」と「Sessionへ保存する」は違う

今回の問題から、

```java
if (languageVariant == null) {
    languageVariant = LanguageVariant.MAINLAND;
}
```

と、

```java
session.setAttribute(
        "languageVariant",
        LanguageVariant.MAINLAND
);
```

は全く違う処理であることを再確認した。

前者は、

```text
この処理の中だけMAINLANDとして扱う
```

ものであり、後者は、

```text
以後のリクエストでもSessionからMAINLANDを取得できる
```

ものである。

Sessionにデフォルト値そのものを保存しない設計にするのであれば、

```text
languageVariant == null
→ MAINLAND
```

というルールを、`languageVariant` を利用する各処理で適用する必要がある。

現在は、

```text
/practice/menu
/practice/start
```

の両方で同じ判定が必要になっている。

今後さらに同じ処理が増える場合は、Controllerごとに同じコードを書くのではなく、

```text
Sessionの設定値を取得
        ↓
未設定ならデフォルト値を返す
```

という処理を共通化することも検討する。

## 12. 今回の実装で得たこと

今回の発音表記対応では、単に拼音・注音を画面へ表示するだけでなく、既存データを持つDBの変更、Sessionによる設定管理、仕様変更に伴うドキュメント更新など、複数の課題が発生した。

特に今後に活かしたい点は以下である。

- 既存データがあるテーブルへNOT NULLカラムを追加するときは段階的に変更する
- 制約追加前は「入力したつもり」ではなくSQLでNULLの有無を確認する
- 既存の実装パターンを新機能へ応用する
- 学習支援情報は表示するだけでなく非表示にできることも重要
- 実際の利用習慣だけでなくUIの一貫性や実装コストも仕様判断に含める
- 理想的な実装と、現在のプロジェクトにとって最善の実装は必ずしも一致しない
- 本解答に機能を追加するときは別解など同じ性質を持つデータも確認する
- テストデータが単純すぎると、実際に必要なケースを見落とす可能性がある
- ローカル変数へのデフォルト値設定とSessionへの保存を混同しない
- 同じデフォルト値判定が複数箇所に現れた場合は共通化を検討する

今回特に大きかったのは、**機能を追加することそのものより、その機能が既存のデータ・画面・設定・ドキュメントへどこまで波及するかを見る必要がある**と分かったことである。
