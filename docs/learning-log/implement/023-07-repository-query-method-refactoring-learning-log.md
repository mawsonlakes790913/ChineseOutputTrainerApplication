# 023-07 Repositoryのクエリとメソッド名の整理 — 学習ログ

## はじめに

機能追加を重ねるにつれてRepositoryのメソッド数とクエリが増え、処理の目的を把握するためにSQLを細かく読む必要が生じていた。今回の作業は新しい機能を追加するものではなく、**既存の検索・更新・削除処理の意味を保ちながら、今後も自分で保守しやすい状態に整える**ためのリファクタリングだった。

## 1. Repositoryの読みやすさはクエリ以外でも決まる

長いSQLが書かれたメソッドでは、検索条件をすべて読んで初めて用途が分かることがある。そこで、各メソッドの直前に「何を取得・更新・削除する処理か」を示すコメントを追加した。

Repositoryはデータベースとのやり取りを担う層だが、呼び出し側から見ればメソッド名も重要なインターフェースである。**SQLの正しさに加えて、メソッド名とコメントだけで役割を推測できること**が、保守性につながると分かった。

## 2. JPQLとNative Queryは参照する対象が異なる

JPQLはEntityとそのプロパティを対象に記述する。一方、Native Queryはデータベースのテーブル名やカラム名を直接記述する。例えば、ユーザーのAI生成履歴を削除する処理では、JPQLの`DELETE FROM AiGenerationHistory a WHERE a.user.id = :userId`を、Native Queryの`DELETE FROM ai_generation_history WHERE user_id = :userId`へ変更した。

今回、使い慣れているNative Queryへ一部の処理を揃えたのは、テーブル・カラムとの対応を追いやすくするためだった。ただし、**Native Queryの方が常に優れているという意味ではない**。Entityの関連を利用した更新では、JPQLのままの方が扱いやすい場合もある。

その例が`QuestionRepository.replaceStructure(...)`である。このメソッドは`Structure`型の引数を受け取り、問題が参照する構文を別の構文へ変更する。Native Queryへ置き換えるとIDを扱う形に変更する必要があり、`AdminStructureService.deleteStructure()`など呼び出し側にも修正が及ぶ。そのため、この処理はJPQLを維持した。

**記述方式を統一するためだけに、変更範囲を広げるべきではない**という判断が重要だった。

## 3. ページングでは取得用クエリと件数用クエリの整合性が必要

`UserRepository.findUsers(...)`をNative Queryへ変更する際、`Page<Users>`を返すための`countQuery`も明示した。

取得用クエリにはログインID、アカウント状態、メールアドレスによる絞り込みと並び順を指定している。一方、件数用クエリでは**同じ絞り込み条件を使いながら、`ORDER BY`は不要**となる。

もし取得用と件数用で検索条件が食い違えば、画面に表示されるデータと総件数・ページ数が一致しなくなる。ページングを伴うRepositoryの修正では、SQLが実行できることだけでなく、**一覧取得と件数計算が同じ対象集合を見ていること**を確認する必要がある。

## 4. `@Query`を使うメソッド名は用途を優先できる

Spring Data JPAの派生クエリでは、`findBy...And...`のようにメソッド名から検索条件を組み立てる。一方、`@Query`を指定したメソッドでは、検索条件はクエリ本文に定義される。

この違いを踏まえ、長い条件列挙型の名前を用途中心の名前へ整理した。例えば、非ログインユーザー向けの問題取得を`findAnonymousPracticeQuestions(...)`、ログインユーザー向けを`findPracticeQuestions(...)`とし、件数取得メソッドとの対応も分かりやすくした。

同様に、`findFilteredUserQuestionList(...)`は`findUserQuestionList(...)`へ、複合主キーの構造を名前に含めていたお気に入り削除処理は`deleteByUserId(...)`へ変更した。`@Query`で条件を明示している以上、**内部の条件をすべて名前に書くよりも、呼び出し側が何を依頼しているかを表す方が読みやすい**。

ただし、名前を変更した場合は、Repositoryだけでなく呼び出し元のメソッド呼び出しも合わせて修正する必要がある。

## 5. リファクタリングでは振る舞いを変えないことが前提

今回の変更では、削除対象の条件、一覧の絞り込み、並び順、ページング、そして023-06で整備した所有者によるアクセス制限を維持することが前提だった。特に検索条件が複雑なRepositoryでは、読みやすく書き換えたつもりでも、括弧や条件の組み合わせによって取得対象が変わる可能性がある。

元の記録には、この整理に対する個別の動作確認結果は残っていない。そのため、動作検証まで完了したとは断定せず、今後の同種の変更では取得件数・検索結果・削除対象などを変更前後で比較する必要があると整理した。

## まとめ

今回学んだのは、Repositoryの保守性はSQLの書き方だけでなく、**コメント、メソッド名、クエリ形式、呼び出し側との関係**によって決まるということだった。

JPQLとNative Queryのどちらかに機械的に統一するのではなく、既存の振る舞いと変更範囲を考慮して選ぶ。また、`@Query`で処理を定義したメソッドは、条件の列挙より用途が伝わる命名にする。こうした判断の積み重ねが、機能追加後のコードを継続して保守できる状態につながる。
