# 009 復習モードの実装 その1 - 検索条件とクエリ設計

## 1. 今回やったこと

復習モードの実装を開始した。

復習モードは通常学習と基本的な構造は似ているが、出題対象が「一度学習して理解度を保存した問題」になる。

今回は復習問題そのものを出題するところまでは進めず、まず `/review/menu` で、

- 難易度
- 理解度
- お気に入り状態

を指定し、その条件に該当する復習問題数を表示するところまで実装した。

通常学習ではメニューを開いた時点で問題範囲と問題数が表示されている。

一方、復習モードでは、

```text
復習メニューを開く
↓
全復習対象問題数を表示
↓
ユーザーが検索条件を変更
↓
条件に該当する問題数を再取得
↓
画面上の問題数を更新
```

という動きになる。

そのためControllerにも、単純にメニュー画面を表示する `/review/menu` だけではなく、JavaScriptから呼び出して問題数だけを返す `/review/count` が必要になった。

同じメニュー画面を扱う処理でも、「画面そのものを返す処理」と「画面の一部分で使用するデータだけを返す処理」が存在する点は、通常学習との大きな違いだった。

---

## 2. 復習問題の検索条件

復習対象の問題は、`study_history` に学習履歴が存在する問題の中から検索する。

難易度と理解度については、どちらも複数選択できるため、

```sql
sh.evaluation IN (:evaluations)
q.difficulty IN (:difficulties)
```

として絞り込むことができた。

この2つについては比較的単純だったが、お気に入り状態による検索は少し考える必要があった。

---

## 3. お気に入り登録されていない問題をどう検索するか

今回特に考えたのがお気に入りの検索方法だった。

復習メニューでは、

- お気に入り登録済みの問題のみ
- お気に入り未登録の問題のみ
- お気に入り状態に関係なく両方

の3種類を選択できるようにした。

最初の「お気に入り登録済み」だけであれば、`favorite` テーブルに存在する問題を検索すればよい。

しかし、「お気に入り未登録」を検索する場合は逆になる。

お気に入り未登録の問題には、そもそもそのユーザーと問題の組み合わせに対応するレコードが `favorite` テーブルに存在しない。

つまり、

```text
お気に入り登録済み
→ favoriteにレコードがある

お気に入り未登録
→ favoriteにレコードがない
```

という「レコードが存在しないこと」を検索条件として扱う必要があった。

そこで `study_history` と `favorite` を `LEFT JOIN` した。

```sql
LEFT JOIN favorite f
  ON sh.user_id = f.user_id
 AND sh.question_id = f.question_id
```

`LEFT JOIN` であれば、`favorite` に対応するレコードが存在しない問題も検索結果から消えず、`f` 側が `NULL` の状態で残る。

そのため、

```text
f.question_id IS NOT NULL
→ お気に入り登録済み

f.question_id IS NULL
→ お気に入り未登録
```

として区別できる。

最終的に、

```sql
AND (
    :favoriteCondition = 'ALL'

    OR (
        :favoriteCondition = 'FAVORITED'
        AND f.question_id IS NOT NULL
    )

    OR (
        :favoriteCondition = 'NOT_FAVORITED'
        AND f.question_id IS NULL
    )
)
```

という条件にした。

### ALLの場合

```sql
:favoriteCondition = 'ALL'
```

が `true` になるので、OR全体が `true` になる。

そのため、お気に入り登録の有無による絞り込みは行われない。

### FAVORITEDの場合

```sql
f.question_id IS NOT NULL
```

を条件にすることで、`favorite` にレコードが存在する問題だけが対象になる。

### NOT_FAVORITEDの場合

```sql
f.question_id IS NULL
```

を条件にすることで、`favorite` にレコードが存在しない問題だけが対象になる。

今回の実装で特に重要だったのは、**「お気に入り未登録」という状態を直接保存しているわけではない**という点だった。

「未登録」というデータを検索するのではなく、

```text
LEFT JOINする
↓
対応するレコードがない
↓
NULLになる
↓
IS NULLで未登録と判断する
```

という形で取得することになった。

理解度や難易度のように「列に保存されている値」を検索する場合とは考え方が異なり、今回の検索条件の中ではここが最も工夫を要した。

## 4. 「すべて」をどう扱うか

今回、理解度や難易度について何も選択されていない場合は「すべて」を意味するようにした。

そのため、例えば理解度が未選択なら、

```text
HARD
GOOD
EASY
```

のすべてをRepositoryへ渡す。

お気に入り条件についても、指定されていなければ `ALL` とする。

画面上で「何も選んでいない」ことをそのまま検索条件として扱うのではなく、Serviceへ渡す前に、

```text
理解度未選択
→ HARD / GOOD / EASY

難易度未選択
→ BEGINNER / INTERMEDIATE / ADVANCED

お気に入り条件なし
→ ALL
```

という検索可能な値へ変換する形にした。

既存の `SearchConditionConverter` に理解度とお気に入り条件の変換処理を追加したことで、ControllerやRepository側に変換処理を散らさずに済んだ。

## 5. conditionを検索フィルターから外した

今回、途中で設計を変更した部分が `question.condition` だった。

当初は復習モードの検索条件を、

- 難易度
- 理解度
- condition
- お気に入り状態

の4種類にする予定だった。

`condition` は複数選択できるようにし、何も選択されなければすべてのconditionを対象にする設計としていた。

実際に、最初は以下のようなクエリまで作成した。

```sql
SELECT COUNT(*)
FROM study_history sh
JOIN question q
  ON sh.question_id = q.question_id
LEFT JOIN favorite f
  ON sh.user_id = f.user_id
 AND sh.question_id = f.question_id
WHERE sh.user_id = :userId
  AND sh.evaluation IN (:evaluations)
  AND q.difficulty IN (:difficulties)
  AND (
      :includeAllConditions = true
      OR q.condition IN (:conditions)
  )
  AND (
      :favoriteCondition = 'ALL'
      OR (
          :favoriteCondition = 'FAVORITED'
          AND f.question_id IS NOT NULL
      )
      OR (
          :favoriteCondition = 'NOT_FAVORITED'
          AND f.question_id IS NULL
      )
  )
```

`includeAllConditions = true` ならconditionによる絞り込みを無効にし、`false` なら、

```sql
q.condition IN (:conditions)
```

によって選択されたconditionだけを検索する仕組みだった。

クエリとしては実装できたが、その後、実際に `condition` に何を登録するのかを考えたことで問題が出てきた。

### conditionを具体的にすると答えのヒントになる

例えば、

```text
就算～也～
不是～而是～
除了～之外，也～
既然～就～
越～越～
```

のような値を登録することを考えた。

しかし、これを復習メニューの検索条件として表示すると、

```text
「不是～而是～」を選択
↓
その表現を使用する問題だけが出題される
```

となる。

瞬間作文で中国語を自分で考える問題なのに、出題前から使用する表現がかなり分かってしまう。

検索条件としては分かりやすいものの、問題を解くという観点では具体的すぎた。

### conditionを抽象的にしてみる

そこで、

```text
接続詞
副詞
介詞
```

のような大きな分類にすることも考えた。

しかし、今度は、

```text
接続詞の問題だけ復習する
副詞の問題だけ復習する
```

というフィルターが、実際の復習でどの程度必要なのか疑問が出てきた。

つまり、

```text
conditionを具体的にする
↓
分類として分かりやすい
↓
しかし答えに近い情報になる

conditionを抽象的にする
↓
答えのヒントにはなりにくい
↓
しかし検索フィルターとしての有用性も低くなる
```

という状態になった。

ここで、そもそも `condition` を何のために用意しているのかを改めて考え直した。

---

## 6. conditionは検索条件ではなくヒントとして使う

`condition` は削除するのではなく、**役割を変更する**ことにした。

例えば問題を見ても使用する中国語表現が思いつかなかった場合に、

```text
ヒント：不是～而是～
```

のように表示するのであれば、具体的な文法や言い回しを登録しておく意味がある。

検索フィルターとして考えたときには「具体的すぎる」という問題だったものが、ヒントとして考えれば逆に「具体的であること」が役に立つ。

そのため、

```text
condition
× 復習問題を絞り込むための検索条件

condition
○ 問題回答時に必要に応じて確認するヒント
```

と役割を整理した。

最終的に復習モードの検索フィルターは、

- 難易度
- 理解度
- お気に入り状態

の3種類とした。

一度実装した `conditions` や `includeAllConditions` に関係するRepository、Service、Controller、HTML、JavaScriptの処理についても削除した。

今回のように、技術的には実装できる機能であっても、**実際にその機能をどう使うのかを考えた結果、実装しない判断をすることもある**と分かった。

特に今回は `condition` 自体が不要だったのではなく、「検索」と「ヒント」のどちらで使う情報なのかを整理したことで、役割が明確になった。

## 7. JavaScriptから問題数だけを取得する

今回の復習メニューでは、検索条件を変更するたびにページ全体を再読み込みするのではなく、JavaScriptから `/review/count` を呼び出すようにした。

```text
検索条件を変更
↓
changeイベント
↓
選択中の条件をURLSearchParamsへ追加
↓
fetch("/review/count?...")
↓
対象問題数を取得
↓
画面の問題数だけを書き換える
```

という流れになっている。

また、ページを最初に開いたときにも `updateCount()` を実行することで、検索条件を操作する前から全復習対象問題数を表示できるようにした。

通常学習のようにControllerが最初から問題数をModelへ設定する方法とは異なり、今回は同じ `/review/count` を、

```text
初回表示
検索条件変更時
```

の両方で利用している。

これによって、初回表示用と検索条件変更用で問題数取得処理を分ける必要がなくなった。

## 8. 実装を終えて

通常学習と基本的な構造は似ているため、復習機能そのものの流れがまったく分からないということはなかった。

ただし、メニュー画面の仕組みは通常学習より複雑だった。

通常学習では最初から問題範囲と問題数を表示できるのに対し、復習ではユーザーごとの学習履歴に加えて、

```text
理解度
難易度
お気に入り状態
```

を組み合わせて対象問題を決める必要がある。

特に時間がかかったのは、お気に入り登録済みだけではなく**お気に入り未登録の問題も検索対象にする処理**だった。

`favorite` にレコードが存在しないことを `LEFT JOIN` と `IS NULL` で判定する形にしたことで、3種類のお気に入り条件を1つのクエリで扱えるようになった。

また、途中まで実装していた `condition` フィルターを最終的に削除したことも今回の大きな変更点だった。

実装できるかどうかだけで判断するのではなく、

```text
この情報は何のために存在するのか
↓
検索条件として本当に必要なのか
↓
問題を解く際のヒントとして使った方が適切ではないか
```

と考え直したことで、`condition` の役割を整理できた。

Repositoryについては、JPQLで書いた方が簡潔になる処理もあったが、今回はRepository内のクエリの統一性を重視してネイティブクエリで実装した。:contentReference[oaicite:2]{index=2}
